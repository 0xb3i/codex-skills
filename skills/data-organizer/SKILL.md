# 数据整理

## 适用范围

本 Skill 负责用户查找和比较的数据、文档与派生产物。以下浅层目录、`scripts/` 与 `tests/` 规则用于此类工作区；已有代码仓库、包、技能目录或框架的结构契约优先。涉及源码移动和依赖变更时由 `$code-master` 处理，不把源码搬进数据整理脚本的 `_organized/`。

## 核心原则

以用户查找方便为第一目标：先看文件应该如何被人找回，再决定目录和文件名。整理优先级是：**高频核心工作文件留在当前主题根目录 > 代码按职责归入 `scripts/` / `tests/` > 其余文件再按业务主题归组**。默认保持浅层结构：`主题文件夹/文件`；如果目标根目录本身已经是主题目录，直接使用 `文件`，不要再套同义父目录或子目录。主题目录原则上至少要容纳两个需要一起查找的文件；若只会放一个普通文件，就把主题写进文件名并直接放在父目录。只有工具强制结构、独立包/数据集边界或后续会稳定承载多个文件时，才保留单文件目录。最多只在确有必要时增加第二层。

“浅层”不是把所有文件都摊在一层。主题目录中的执行脚本、构建脚本、转换脚本统一收进 `scripts/`，测试代码和测试辅助代码统一收进 `tests/`；这两个目录表达的是稳定职责，不属于应避免的纯扩展名分类。少量、关键、需要频繁人工打开的数据或结果（常见为 JSON、XLSX、CSV）则可直接留在主题根目录：只要数量不拥挤、名称清楚，就不要为了形式统一额外套 `data/`、`json/`、`xlsx/` 或同名主题子目录。只有核心数据已经多到影响浏览，或存在清晰的数据集/批次边界时，才继续分组。

## 工作流

1. 递归扫描目标目录，排除 `.git`、`node_modules`、`__pycache__`、系统缓存和已生成的整理目录。先标出三类资产：高频核心工作文件、脚本、测试；不要让后续的主题或扩展名归组覆盖这三类判断。
2. 先定义一条适用于目标目录的命名契约并生成完整的旧路径→新路径计划，不直接动文件。先区分代码运行路径与人工阅读资料：仅代码相关路径要求英文，报告、通知、规范及其主题目录优先保留清晰中文名；层级只保留实际需要的阶段、对象和变体。可用 `scripts/organize_files.py <folder> --out plan.json` 做初扫，但计划必须覆盖跨目录的一致性，不能逐文件各自缩写。
3. 先处理稳定职责：脚本归 `scripts/`，测试归 `tests/`；再按主题归组其他文件，而不是只按扩展名归档。优先使用：项目名、客户/对象名、日期批次、数据集名、报告主题、共同文件名前缀。少量高频核心数据保留在当前主题根目录，不机械归入子目录。
4. 压平目录：先统计每个计划主题的有效文件数；只有一个普通文件的主题直接落为 `<目标根>/<带主题的简洁文件名.ext>`，不要创建单文件子目录。至少有两个需要共同查找的文件，或存在稳定的独立边界时，才使用 `<目标根>/<主题>/<简洁文件名.ext>`。避免把旧目录结构原样搬过去，也不要创建同义套娃目录；但单目录里如果堆了十几个以上共享长前缀的文件，不要为了“扁平”全塞一层，应拆成 `<目标根>/<主题>/<子主题>/<短文件名.ext>`。
5. 简化文件名：去掉无意义词、重复目录名、`final_final`、副本标记、无用途的日期串；两个以上 sibling 共享的前缀可提升为公共目录。资料名称以看懂和检索为先，保留正式标题的关键语义、发布机构、适用年级及有效版本，不为缩短名称将中文规范或通知改成含糊的英文单词。先精简语义，再处理分隔符；不要把旧长名机械拼接或逐词翻译。
6. 审阅产物优先合并：同一对象的多个 review HTML、报告、截图索引或 demo 说明，如果用户通常会横向比较，优先合成一个总览文件（如对象目录内的 `review.html`），保留原始训练/数据文件，删除或替换分散的派生审阅文件。
7. 清理废文件：删除高置信临时/缓存/备份文件；对不确定的“old/废弃/test/测试”文件先列入计划，只有能从内容或同目录上下文确认无用时再删除。Codex 本轮刚生成且已被合并替代的临时/demo/review 派生文件可直接清理。
8. 执行后做一次复扫，按用途核对命名：代码相关路径遵循英文及工程契约，人工阅读资料名称清楚、易检索，中文和有意义的分隔符不视为违规；确认没有空目录、无稳定边界的单文件目录、重复目标名、过深路径和明显遗漏；并逐组比较同级并列目录的语义结构，不能让同一位置在一项中表示日期、另一项中表示版本或批次。重点复查脚本与测试是否仍和数据混放，同时确认少量核心数据没有被无意义地下沉。发现无必要的单文件目录时继续压平，并在需要时把目录主题补进文件名；若目标目录顶层仍有一串同主题 sibling 文件、共享长前缀文件、重复派生产物或应一起审阅的报告/索引文件，判定整理未完成，继续按主题归组，直到顶层只剩少量真正有分组价值的职责目录、主题目录或核心独立文件。

### 路径迁移的依赖检查

文件夹改名或移动前，必须搜索旧绝对路径、相对路径及拼接路径，检查涉及的代码文件、import、配置、测试、启动命令和文档；将引用更新纳入同一迁移计划，涉及源码时按 code-master 执行。移动后同步修改所有有效调用方，优先复用统一路径配置，再复搜旧路径并实际验证受影响入口能读取新位置。不能只改文件夹和文档链接；历史日志、冻结协议或实验快照中的旧路径作为溯源记录保留，需在当前索引说明映射，不改写原始哈希。数据库及锁须先确认占用与读写生命周期，再迁移，避免产生两份状态。

### 单子目录硬闸门

执行移动前和完成后都要逐层统计直接子项。若目录 `A/` 只有一个普通子目录 `B/`，且 `A/` 没有其他文件或并列对象，默认必须把 `B/` 内容上提到 `A/`，不能仅因 `B` 能表达对象名、方法名或未来可能扩展就保留这一层。只有框架强制布局、独立包/权限边界或已经存在两个以上真实并列对象时才能例外；未来可能出现的对象不算依据。计划中出现 `阶段目录/唯一对象目录/文件` 时，必须先证明例外，否则计划不通过。

## 判断归属

- 同一项目的资产保持在同一主题边界内，但主题根目录内部继续按职责分层：脚本进 `scripts/`，测试进 `tests/`，少量高频核心数据和结果表可直接留根部。
- 同一对象的不同格式版本放一起，例如 `csv/xlsx/pdf/png`。
- 同一时间批次但主题不同，不强行合并；日期只作为辅助标识。
- 不要创建 `图片/文档/表格/JSON/XLSX` 这种纯格式目录，除非用户明确只按文件类型找。`scripts/` 与 `tests/` 是职责目录，不受此限制。
- 对混乱目录，先用文件名和父目录名归组；必要时抽样读取文件头或元数据确认。

## 命名规则

- **英文要求仅限代码及运行相关路径**：源码目录、包、模块、脚本、测试及明确作为程序接口的配置或产物路径，使用清晰英文并遵循仓库及工具链约定，便于导入、执行和维护。已有用户工作区根目录及第三方约定不因此强制改名。
- **人工阅读资料允许并优先使用中文**：报告、通知、论文规范、说明、会议材料及相应主题目录，以容易理解和检索为准；原名清晰就保留，不强制翻译或缩写，英文原始资料也不必反向强制翻译。放在代码仓库或 `docs/` 内，不代表文档名称必须英文；程序读取文档应正确处理路径，仅有明确工具限制时才另定路径契约。
- **同级同用途命名一致，同义目录合并**：同一资料父目录下，自有主题目录和资料文件统一语言；中文资料区不并列 `methods/` 与 `研究方法/` 这类中英文同义目录，应合并为清晰的中文主题。文档被程序读取或参与内容哈希校验，不构成另建英文资料目录的理由；迁移时同步代码引用、验证内容哈希和实验兼容性。代码职责目录、框架入口和英文原始文献仍按各自已有契约保留，不机械翻译。
- 利用父目录表达上下文，每个语义只出现一次；阶段、对象、变体只在有实际区分价值时形成层级，不机械套满三层。
- 工程职责目录可用 `scripts`、`tests` 等英文名；资料主题目录可用 `论文规范`、`项目通知` 等中文名，文件可用 `论文格式规范（2026年6月修订）.doc`、`开题通知.pdf`。保留已有合理布局，避免为统一语言批量搬迁。
- 代码名称采用简洁英文，必要时用 `postPilot.py` 等驼峰名，分隔符遵循工程约定。资料名称可保留中文标点、空格及有意义的分隔符；避免含义不明的缩写和难读的长串拼接。
- 日期、样本数、模型名、`full`、`final`、`predictions` 等只有在父目录内承担真实区分作用时才保留；运行批次包含至少两个文件时，优先把批次提升为目录。
- 同级并列对象使用相同的命名 schema 和 token 顺序；需要表达不同维度时下沉到各对象内部，不能在同一个 token 位置混用日期、版本号、模型或批次。
- 同一对象的不同格式若语义相同，使用相同 basename；若语义不同，用最短的语义变体区分，不把格式名重复写进 basename。
- 同名冲突时先用最短的语义区分词；仍需编号时追加 `2`、`3`，如 `review2.md` 或 `会议纪要（2）.md`，不加无意义的长哈希。日期在区分批次或文件有效版本时保留，不默认给每个名称加日期。
- 保留扩展名原样；不要为“看起来统一”而转换格式。
- 有明确约束的名称按契约保留：第三方包内部文件、原始数据标识、冻结实验读写接口、框架强制文件名、技能标识等不为命名风格强行改写。普通自有目录不笼统视为例外；可迁移的名称应同步更新引用、导入、配置和文档。运行中的数据库、锁等先核实生命周期，不能仅为改名中断任务或产生第二份状态。

## 删除口径

ZIP 等资料压缩包完整解压后，核对成员数量、内容哈希及文件可读取性，确认没有遗漏或同名覆盖，即删除原压缩包并更新索引，不默认同时保留解压文件和原包。仅部分解压、解压失败或仍被程序直接读取的归档不算冗余副本；先补齐解压或处理依赖，再删除。

可清理本轮已用完的临时产物，以及确认无引用、无用户工作内容的系统元数据和缓存。`*.tmp`、`*.bak`、`*.old`、`*.orig`、`*.swp`、`~$*` 等名称只能提示候选，不能单凭后缀判定可删；编辑器或办公软件仍在使用的临时文件也要保留。

名称含 `test`、`测试`、`草稿`、`draft`、`old`、`废弃`、`deprecated` 的文件，先确认不是唯一版本、训练/评估所需样本或用户可追溯的来源文件，再执行已核实的清理。

## 工具脚本

[scripts/organize_files.py](scripts/organize_files.py) 只做第一轮按名称推断的计划草稿，不能判断源码依赖、用户文件价值或脚本/测试的真实职责：

```bash
python3 "${CODEX_HOME:-$HOME/.codex}/skills/data-organizer/scripts/organize_files.py" /path/to/folder --out /path/to/work/plan.json
```

脚本只输出 `moves` 与 `cleanup_candidates` 草稿，不移动或删除来源文件。词法推断只作归组线索，可能过度截短正式标题；中文与有意义的分隔符本身不是问题，审阅草稿时应保留资料的可读性和版本信息。检查草稿后按本 Skill 的职责、命名和删除规则修正，再执行核实后的逐项移动与清理。计划放在扫描目录外的临时工作区，完成后删除。
