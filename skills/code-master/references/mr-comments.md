# MR 评论交付

## 授权与范围

当前任务明确要求发布、回复评论，或用户明确调用包含评论发布的工作流时，按授权执行。只要求审查 MR/PR 时先交付对话结论；公开技能不能继承其他用户或历史任务的发布授权。用户本次要求“只看不发”或“先给草稿”时按其要求交付。

默认不另建报告文件、不发总评占位评论。零缺陷在对话中说明范围和验证限制；用户明确要求发布总评时才发布。证据不完整的疑点留在对话中。评论授权只覆盖指定目标与相关线程，不包含审批、合并或其他渠道消息。

## 发布前核对

1. 按[仓库访问](repository-access.md)读取目标仓库、MR/PR 状态、base/head commit，保留审查版本。每条评论发送前重新确认版本与状态。版本变化时重读新 diff 和受影响上下文，重新核实根因与行号；已关闭或合并时在对话说明，不默认追发。
2. 用户指定旧版本时固定该版本审查；只有问题在最新开放版本仍存在且已核对当前定位，才发布到当前版本。历史版本问题在对话注明所属版本。
3. 读取全部普通评论、review notes 和线程，包括已解决线程。按分页和完整性信号补全；读取失败时先解决，不能假定零评论。
4. 按文件、函数、根因和触发条件做语义去重。已有未解决同根因评论时跳过；已解决时先核对修复和解决原因。确有再次引入才作为新问题，并说明与原线程的关系。
5. 核验 `final_comments.json`，将每条完整正文准备为结构化字符串或临时请求文件，绑定当前审查版本与最小新侧行区间。

## 正文

每个独立根因一条，优先说明触发条件与实际影响，再给修复方向。语言遵循用户与目标仓库约定，默认中文：

```text
[P1] 单条返回被误判为旧协议

接口仅返回一个商品时，适配器会返回 JSON 字符串。这里仅接受列表，导致正常结果进入旧协议分支并报字段缺失。

建议统一解析适配器返回形态，再区分协议，并补单条结果回归测试。

验证：已用实际解析函数离线复现；未调用远端接口。
置信度：10/10。
```

保留必要的契约、规则证据或复现输入，不贴冗长过程报告或重复 diff，不包含凭据和敏感日志。可加隐藏标记 `<!-- code-master:<fingerprint> -->`，基于仓库、目标、文件、函数与根因生成，不绑定易变行号或 commit。标记辅助识别，语义去重仍须执行。

## 发布与回读

优先使用宿主连接器或 CLI 的结构化参数。GitHub 行级评论使用真实 REST 接口：

```text
POST repos/{owner}/{repo}/pulls/{pull_number}/comments
```

请求字段为 `body`、`commit_id`、`path`、`side: RIGHT`、`line`。多行评论另传 `start_line` 和 `start_side: RIGHT`；`line` 为结束行。`commit_id` 使用已复核的 head SHA。先用平台接口文档或工具帮助核实锚点约束；不能把 MR 内部标识和页面编号混用。

将 JSON 请求写入临时文件，再通过参数数组执行 `gh api --method POST <endpoint> --input <request.json>`，或直接提交连接器结构化参数。避免 shell 拼接正文，认证沿用当前工具配置。

- 逐条串行发送，成功后立即回读具体评论，核对正文、文件、新侧行号、绑定 commit 与评论 ID，再发送下一条。
- 检查 API 错误与实际评论对象；退出码或 HTTP 状态不能代替回读证据。
- 超时或响应丢失时先完整重读列表，按正文、标记、锚点与时间确认是否已创建。确认未创建且原因可恢复后才补发；状态仍不确定就停止并报告，避免重复发送。
- 权限拒绝时停止，报告实际原因。部分成功只继续未完成项，不从头重发整批。
- 原线程回复使用平台对应回复接口，保留线程关系；不得通过新增独立评论冒充回复。

对话交付问题严重度数量、已新增/已存在/未发出数量、目标或线程链接及必要验证限制。只有回读成功的评论计为已发布；完成后清理本次请求文件与审查数据。
