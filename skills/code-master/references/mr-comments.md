# MR 评论交付

## 默认行为与范围

用户已于 2026-09-14 明确授权：给出 MR/PR 并要求代码审查时，将核实的问题直接发布到该 MR，无需再问是否发送。这是本用户维护版本的默认输出方式；用户本次明确要求“只看不发”“先给草稿”时不发布。单纯讨论技能、查看 MR 信息或审查本地 diff 不触发发布。用户明确要求的评论优先于仓库“默认不自动发总结评论”的惯例；不因此扩大为修改源码、合并 MR、审批、回复无关线程或发消息到其他渠道。

默认不生成 HTML/Markdown 报告文件，也不发总评占位消息。0 缺陷通常只在对话汇报；但用户给出 MR 并显式说“CR”时，0 缺陷也在 MR 发布一条简短结论，说明审查版本、范围和验证限制。非零缺陷由行级评论承载结论，不再重复发总评。有待业务确认、证据不完整的疑点留在对话，不把假设当缺陷发出。

## 发布前：目标、版本、去重

1. 使用 `bytedcli --json codebase mr get <MR URL>` 读取仓库、MR 内部 Id、最新 version、BaseCommitId/SourceCommitId/版本 Id，保留审查版本。每条评论发布前再次确认这些值和 MR 状态；若版本已变化，自动重新读取新 diff 和受影响上下文、重新映射行号并核实问题，不能把旧行号发到新版本。MR 已关闭/合并则在对话汇报，不默认追发。
2. 用户指定旧版本时，审查该版本并保留绑定；只有问题在最新 open MR 中仍存在且已核对当前行号才发布，否则在对话注明它只属于历史版本。
3. 读 `bytedcli --json codebase mr comment list <MR URL>` 的全部线程与 review notes，不仅查询自己的或 open 线程。先看实际返回的分页/完整性信号；读取失败或内容不完整时先解决读取，不能假设零评论。
4. 按文件、对应函数/代码段、根因和触发条件做语义去重，不能只比标题或行号。已有未解决同根因评论时跳过；已解决同根因评论时先核对修复与解决原因，不能默认重发或重开。只有当前代码确有可证明的再次引入才作为新问题评论，并说明与旧线程的关系。
5. 对每条待发布缺陷确认它源于本次新代码，锚定最小的新侧行区间。校验 `final_comments.json` 后，将完整正文准备为内存字符串或工作目录临时正文文件；不把 shell 字符串拼接当作转义。

## 评论正文

每个独立根因一条，中文，优先解释触发条件和实际影响，再给修复方向。例如：

```text
[P1] 单条返回被误判为旧协议

当接口只返回一个商品时，适配器会返回 JSON 字符串。这里仅接受列表，导致正常结果落入旧协议分支并报字段缺失。

建议：先统一解析适配器返回形态，再区分新旧协议，并补单条结果回归测试。

验证：已用实际解析函数离线复现；未执行线上接口。
置信度：10/10。
```

保留必要的上游契约、具体规约链接或复现输入，不贴冗长过程报告、不重复整段 diff、不泄露 token/日志敏感字段。可以追加稳定的隐藏标记 `<!-- code-master:<fingerprint> -->`，fingerprint 基于仓库、MR、文件、函数与根因；不包含易变行号/commit。已有评论使用历史标记时，仍按正文、锚点和根因识别，不因标记前缀变化重发。标记辅助重复发送检测，不能代替语义去重。

## 串行发布与回读

优先使用当前 CLI/已提供连接器的结构化参数；`bytedcli codebase mr comment create --help` 可核对参数。CLI 支持 `--path --side new --start-line --end-line --body`，但不提供显式 commit 锁定参数；需要绑定审查快照时使用本技能 [codebase-api.md](codebase-api.md) 的 `create-comment`，显式传入四个定位参数：`--repo-id`、`--commentable-id`、`--old-commit-id`、`--new-commit-id`，禁止省略后静默采用最新 commit。MR 的内部 Id 不是页面 number。

正文用 Python `subprocess.run` 的参数数组传入（`shell=False`），或直接调用 `codebase.create_comment(..., content=body, ...)`。认证按 [auth.md](auth.md) 在内存/子进程环境内传递，禁止在命令行传 token。两种方式都只提交已经准备、核实的正文，不能在发布途中让模型改变根因。

- 各条评论串行发送。每条成功后立即通过评论列表回读，核对正文、文件、new 侧行号、Old/NewCommitId、线程/评论 Id；记录已完成状态再发送下一条。
- HTTP 2xx 或 CLI 退出码 0 不等于成功，还要检查 API 错误对象及实际 Comment/Id；没有回读证据不能计入成功数。
- 超时、网络断开或响应丢失时，先重新列出评论，按正文/标记、锚点和时间核对是否已经创建；找到就计为成功，不重发。只有完整回读确认未创建且已定位可恢复原因时，才对同一条补发一次；状态仍不确定则停止发布并报告，不能盲重试。
- 权限拒绝停止发布并报告实际原因；不改用其他身份。部分成功时只保留/汇报未完成项，不从头重复整批。
- 评审和评论各自计数：最后只需给问题严重度数量、已新增/已存在/未发出数量、MR 或实际返回的线程链接，以及必要验证限制。不在 MR 再发重复总结。
