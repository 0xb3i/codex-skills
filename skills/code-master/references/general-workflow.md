# 通用检测工作流

先完成[审查模式](review-mode.md)的范围准备，读取 `review_files.md`、实际 diff、[共享工程准则](shared-design.md)与[架构审查](review.md)。所有数据写入本次 `WORK_DIR`。

## 1 读取目标

核对待审文件、审查版本、用户关注范围和 scope。`diff_only` 只报告归因于本次变更的问题；`full_file` 按用户指定的文件、函数或模块检查当前源码，无 diff 也继续。两种 scope 都必须引用实际存在的源码行号。

读取适用的项目规范和规则原文。按实际待审目标统计文件数与变更行数；整文件审查结合文件大小、调用关系判断是否需要分组。

## 2 选择策略

文件数 ≤5 且变更行数 ≤500 的变更直接审查。更大变更按业务功能、调用链或代码层级分组，超过 5000 变更行必须分组。

分组约束：

- 最多六组，覆盖所有待审文件；每组能够理解相对完整的功能与契约。
- 接口、共享类型和公共常量等边界文件加入所有依赖组。
- 两组文件重叠超过各自数量的 50% 时优先合并；分组过多按业务关联合并。
- 写入 `review_groups.md`，记录各组文件、分组依据和审查重点。

存在多个独立分组时，按宿主可用并发槽位分批派发子智能体。每组收到文件列表、审查重点、固定版本、scope、三个根目录，以及以下读取要求：

1. 读取 `SKILL.md`、`shared-design.md`、`review-mode.md` 和本流程。
2. 读取 `review-dimensions.md`、`review-rule.md` 及适用语言专项，独立核实仓库 API 与契约。
3. 执行下方完整检测步骤，输出 `group/group_<num>.jsonl`，每行一个缺陷对象。零缺陷也写出空文件。

只有一组且无需隔离大块上下文时由主流程执行。宿主没有子智能体工具时主流程逐组串行完成，输出相同格式。缺失分组结果表示未完成，必须补做；文件存在后仍需核实检测覆盖与证据。

## 3 检测

### 上下文与边界

读取完整函数、调用方、生产方和消费者，核对真实输入、返回类型、错误语义、状态、并发、配置传播与生命周期。涉及协议迁移、复用或替换时沿相关调用链查到实际消费者，不以固定调用层数代替契约验证。

调查仓库中同职责的 API、类型、组件和基础设施，确认语义、版本与扩展点。新增实现、绕过公共入口、重复事实来源或替换残留需形成证据链：现有符号 → 适用契约 → 偏离位置 → 具体影响 → 准确的复用或扩展建议。合法独立职责与有依据的兼容边界不算重复。

验证对象方法或字段前，读取生产方的实际返回值；注解、变量名、语法合法性和 mock 不能代替运行契约。比较 fixture 与真实返回类型，确认测试进入新增分支且没有 mock 掉待验证的调用。优先让真实生产函数结果经过改动点到达消费者，只隔离外部依赖。受环境限制未运行时保留静态证据和未运行项，语法检查不能称为行为验证。

仅对受影响的跨模块边界生成 `boundary_checks.md`，分组时使用 `group/boundary_<num>.md`，记录生产方、实际类型、改动动作、消费者与验证证据。

### 维度与语言

逐项执行[七维度清单](review-dimensions.md)，检查变更代码与上下文交互。按实际文件读取 [Go](lang-go.md) 或 [TypeScript / JavaScript](lang-typescript.md) 专项。其他语言依据通用维度和仓库规则。

`diff_only` 不报告独立于本次变更的存量问题；删除代码只检查其对存续路径的影响。`full_file` 按显式目标检查存量。发现的问题必须仍存在于审查版本，不能把修复旧问题的变更反向报告为缺陷。

### 定级

按[定级规则](review-rule.md)区分核心功能、条件性功能、防御不足、设计维护与纯风格问题，再确定严重度和置信度。有证据的复用、职责和迁移缺陷按 `QUALITY/P2` 保留；已有功能后果时按实际影响分类。纯风格丢弃，非 P0 且置信度低于 5 的缺陷丢弃。完成定级自检，再填写[缺陷结构](review-mode.md#缺陷结构)。

## 4 汇总与交叉检查

直接审查的缺陷或全部分组结果汇总到 `comments.jsonl`，每条必须有非空标题。核对所有分组完成状态，不能把缺失文件当作零缺陷。

分组审查后复核共享接口、导出函数签名和共享类型的变化：调用方、实现方和使用方是否同步更新。结合 `review_groups.md` 和各组证据补查跨组盲区，新增问题加入统一缺陷池。

## 5 过滤与校验

依次处理统一缺陷池：

1. 按严重度 `P0 > P1 > P2` 排序，同级按置信度降序。
2. 按函数、触发条件和根因去重，同根因保留证据更充分的一条。
3. `diff_only` 对照实际新增行范围核实变更归因；可定位紧邻变更的存续上下文，但必须说明由此次变更引入的影响。`full_file` 不做 diff 行限制。
4. 检查目标文件存在，行号有效，区间指向当前版本的最小相关位置。
5. 读取对应 diff 和源码，确认问题仍存在，排除只属于已删除代码或已被修复的问题。
6. 默认交付最重要的五个独立问题；用户明确要求完整清单时按其范围保留全部已核实问题。

写出 `final_comments.json` 数组，零缺陷为 `[]`，执行：

```bash
python3 "$SKILL_ROOT/scripts/validate_final_comments.py" "$WORK_DIR/final_comments.json"
```

校验失败先修正产物。校验通过只代表结构有效，审查完成还要求全部目标检查、证据与定级复核完成。

## 6 交付

按[MR 评论交付](mr-comments.md)发布已获授权的具体评论，或在对话中给出审查结论与验证限制。评论回读或对话交付完成后，按审查模式清理临时数据。
