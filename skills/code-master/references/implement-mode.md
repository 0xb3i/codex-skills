# 实现模式（implement）

用于创建、修改、修复、重构、迁移或删除代码及工程配置。先读 [共享工程准则](shared-design.md)，再执行本流程。

## 范围与执行门槛

- 普通实现聚焦当前目标及相关模块、调用方、配置和测试，不主动扩大为全仓扫描或大规模重构；不能以改动小为由使用临时补丁。
- 用户明确要求重构、治理、清理或模块化解耦时，在授权范围内额外按 [架构与废弃路径审查](review.md) 检查并实施必要改动。
- 开始实现前明确“参照实现、可复用能力、必须保持的契约、预期差异、验证方式”，用简短进度说明给出关键文件/符号依据。未找到参照时说明搜索范围；不能把尚未查找当作仓库没有。
- 实施中发现新接口、新边界或契约变化时，先补查依据；没有证明现有能力不适用，不新增同职责实现或另一套范式。
- 在正在修改的路径中发现明确、相关且能安全处理的错误、废弃逻辑或无用中间文件时一并处理，不扫描或清理无关区域。保护用户文件，不能仅凭未跟踪状态判断可删除。
- 临时文件确需落盘时集中放入工作目录；交付前核对最终 diff 与行为证据，清除本次非交付产物。这些步骤由智能体自行执行，不是审批流程。

## 目录整理边界

- 源码、包结构、测试布局、导入关系和构建入口由本 Skill 按仓库架构处理，不使用文件名归组工具重排源码。普通实现仅处理相关区域；明确要求的重构任务在授权范围内检查目录健康。
- 只有数据、报告、截图或审阅产物散落、重复、命名失序并妨碍本次任务时，才使用 `$data-organizer` 规划这些资产的路径；常规临时文件清理不额外触发技能。
- 移动文件时同步更新 import、资源路径、注册表、构建配置、文档和测试；不确定归属或会造成大范围公共路径破坏时，不擅自扩大整理范围。

## 实施与验证

1. 先确定目标目录和模块边界；需要整理时先完成受控移动，再修改核心实现及其调用方、配置和测试。
2. 对替换任务执行“旧路径清零”检查：仓内调用方全部迁移到新实现；除有证据的外部契约适配入口外，旧核心实现及其 fallback、开关和注册入口不得残留。公共接口、数据格式或仓外契约需要兼容时，只兼容边界，不保留旧核心行为，除非用户明确要求双轨迁移。
3. 删除旧路径时同步删除只服务旧行为的开关、配置、测试、注释和临时调试代码，避免留下貌似仍受支持的误导线索。
4. 运行与风险相称的验证：优先目标测试，再运行相关 lint、类型检查、构建或集成测试。`py_compile` 只校验语法；修改模块顶层 import、注册入口或共享 core adapter 时，还要用静态检查核对 undefined name、调用关键字和必填参数与真实签名一致，并确认 adapter 返回后不会继续落入旧实现；涉及请求级配置时还要追踪配置从入口到实际消费者的数据流，环境允许时再补模块 import smoke。
5. 验证行为而不只验证语法。覆盖主要成功路径、关键失败路径，以及本次修改最可能破坏的边界。
   交付前逐项核对：①新增/修改的实现是否沿用选定参照；②每个新增抽象、接口、依赖或同职责逻辑是否有必要性依据；③受影响的生产方、消费方及原有调用方契约是否保持或已明确迁移；④实际行为差异是否仅限需求要求；⑤相关验证是否覆盖这些差异与必须保持的不变量。有一项无依据或不符合就返回调查/修正，不得跳过。
   验证预期必须来自需求与真实契约，沿用仓库既有验证手段；根据受影响边界选择正常、缺省、异常及必要的状态/生命周期场景。不能把新实现的输出直接抄成预期，或将需要验证的协作逻辑全部 mock 后声称语义正确；涉及交互时核验边界上的实际行为及副作用。
6. 把清理作为交付硬门槛：验证完成后删除本次创建的全部非交付临时文件，并复查工作区状态，确保没有把备份、草稿、日志、截图、过程报告或中间产物混入最终改动；只有用户明确要求保留或文件本身就是约定交付物时例外。
7. 若环境限制导致某项验证无法执行，说明具体缺口和原因，不把未运行写成通过。

## MR 基线与提交纯净度

仅当用户明确要求创建 MR，或任务本身以已有 MR 为对象并需要更新时，才进入 MR 流程；普通实现任务完成后不得自行创建 MR。进入 MR 流程后，必须读取并执行 [MR 分支整理](mr-branch-hygiene.md)。默认将任务源分支变基到最新目标分支，并剔除不属于本任务的提交；“能合并”不等于“MR 纯净”，最终三点 diff 只能包含本任务改动。只有仓库规则或用户明确禁止改写源分支历史时才改用 merge，并仍须通过同一 diff 纯净度检查。

## 交付

代码修改完成后提供两个部分：

### 实现说明

- 说明怎么改、主要修改或移动了哪些文件、每个改动解决什么问题。
- 简述“参照文件/符号 → 复用能力与扩展位置 → 有意改变的行为”；新增实现或偏离范式时，附上现有能力不适用的具体证据，不能只声称“遵循仓库风格”。
- 若本次是替换重写，明确说明移除了哪些旧路径。

### 验证结果

- 列出实际运行的测试、检查或人工验证及结果。
- 说明验证覆盖了什么行为；存在未验证项或剩余风险时明确列出。
