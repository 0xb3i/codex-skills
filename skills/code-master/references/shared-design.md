# 共享工程准则

实现和审查都必须读取本文件。实现时据此选择方案；审查时据此核实被审代码，不能把“审查”当作跳过仓库调查的理由。仅审查时不实施其中的编辑、删除或迁移动作。

## 仓库调查与设计判断

除非存在真正歧义、破坏性操作或权限边界，不要把检查变成等待用户确认的流程。

1. 阅读适用的 `AGENTS.md`、仓库说明、依赖清单和相关模块。
2. 检查工作区状态，识别用户已有改动，避免覆盖或顺手修改无关内容。
3. 查看相关目录及相邻文件，判断职责分类、命名模式、拥挤程度和目标文件的正确落点。
4. 建立仓库参照：搜索同类功能、公共能力、类型、配置、测试及相关生产方/消费方，选定仍在使用且职责最接近的实现，阅读从入口到输出的相关流程及测试，明确真实的扩展点。参照优先级为适用的仓库明确规范、目标模块当前范式、仓内同职责的成熟实现；不能只凭文件名、单个调用示例或个人习惯作判断。范式冲突时查明适用边界与迁移状态，不照搬废弃路径。
   核对受影响的契约：输入输出的类型与语义、默认值与缺省状态、错误与副作用，以及相关的状态/资源生命周期、执行顺序与并发、配置与上下文传播、兼容边界。以定义、实现、调用方和测试交叉确认；既要检查参数是否能调用，也要检查行为是否符合当前需求，不能假定名称或类型相同就等价。
   跨 Prompt 或模型版本比较同一工具时，先核验是否实际共用同一工具及 Executor 契约；共用契约的参数业务语义不能因 Prompt 措辞不同而改变。工具契约确有版本差异时分别核验，能力指导与设计缺陷和可归责模型的用户损害分别判断。
   没有同类功能时，仍需沿用已有的基础设施和模块组织方式；确无既有仓库或相关基础能力时，依据用户约束、项目依赖和官方契约建立最小必要实现，明确新引入的约定，禁止捏造仓库参照。
   涉及结构化 UI 事件、wire payload 或标签协议时，必须以生产方 schema、真实样例和下游字段契约判定语义；不要再用周边自然语言猜测结构化事件类型，并要验证关键字段（如 ID 与标题）完整到达最终消费者和 Trace。
5. 必要时检查已安装依赖或官方接口，优先使用仓库已经采用且版本兼容的能力。
6. 判断本次需求是增量扩展、新增独立能力，还是新方案接管旧方案的同一职责。只有明确接管同一职责、原行为不再需要或需求要求替代时，才按替换处理；不能仅因数据流、架构或生命周期不同就删除仍被需要的独立能力。合法并存的能力仍须复用共同基础设施，不能以“独立功能”为由复制同职责实现。
   Prompt、序列化 schema 或节点协议升级默认按替换处理：必须同时搜索并迁移配置绑定、生产解析器、缓存/preload、replay adapter、错误轨迹和契约测试；没有明确外部兼容要求时，不得用新旧双轨解析掩盖半迁移。
   为模型行为补 few-shot 时，用简短示例按真实时序呈现历史、当前 query、本请求前置执行结果、意图解读、关键决策理由和期望动作；本请求执行结果放在 query 之后并标明作用域，不写成历史执行，不能为省 token 删掉决定规划路线的理由；沿用已有输出 schema，不重复完整请求、无关状态或长篇 reasoning。只有验证序列化或协议格式本身时才使用完整输入输出示例。 效果验证使用未出现在 demo 中的输入，并保持模型、候选与其余上下文一致比较有/无示例；原题成功只说明定向复现，不能声称泛化问题已修复。
7. 将本次需求分清为必须保持的既有行为和明确需要改变的行为；已有范式能够满足时，直接沿用其落点与扩展方式。只有明确需求、能力缺口、已验证缺陷或不兼容约束要求改变时，才比较必要的替代方案，并说明为什么直接复用或扩展仍不适用；不得为凑方案或个人偏好另起实现体系。



## 五项共同原则

### 区分增量扩展与替换重写

- 新功能确实是稳定方案的增量能力时，在清晰边界内扩展，避免复制逻辑。
- 按上述仓库调查确认新方案取代旧方案后，完成标准不仅是实现新方案，还包括删除被替代的旧实现及其调用、配置、开关、测试和注释；被替代的旧核心仍可运行就视为替换未完成。仍有明确需求的独立能力不属于删除范围。
- **禁止臆造兜底需求。** 不得因为担心新方案失败、追求表面兼容或觉得“留着更安全”，就自行把被替换的旧逻辑作为 fallback、降级分支、feature flag、双写/双读路径或备用实现保留下来。这样会制造双重事实来源、扩大测试矩阵，并误导后续维护者判断旧行为是否仍受支持。
- 只有存在可验证的仓外调用方、公共接口、数据格式、灰度迁移或用户明确要求回滚能力时，才允许保留兼容入口；必须说明具体契约、触发条件和退出条件。无法确认是否存在兼容约束时，先搜索调用方、配置和发布链路，不以永久保留旧核心来规避调查。
- 只复用仍然成立且职责稳定的部分，不为了保留旧代码而扭曲新设计。
- 必须兼容外部公共接口或数据格式时，用小而隔离的适配入口把旧输入转换后统一进入新实现；适配层不能继续运行旧核心逻辑，并要明确其兼容边界。

### 优先复用

- 按“直接复用现有能力 → 在原职责边界内扩展 → 必要时新增实现”的顺序决策，不能跳过前两步。复用对象包括接口、组件、业务逻辑、类型/协议、基础设施、配置及工具链；不局限于工具函数。
- 已有能力覆盖需求时必须调用或组合它，不得复制同职责逻辑、绕过统一入口、另建数据模型或维护第二套规则。需要扩展时保持现有调用方契约；确需改变契约时识别受影响方并完成迁移，不能只让新增路径工作。
- 复用必须保持业务语义和职责归属：沿既有方式完成数据转换、决策、状态变化和资源管理，保持上下游共同依赖的不变量；不得因遗漏参数、隐式默认行为、重复处理或改变执行顺序引入非预期差异。需求要求差异时，在所属边界显式表达并验证，不让差异偶然发生。
- 外部依赖已提供稳定接口时优先调用，不复制其实现；新增依赖前确认现有依赖或标准库不能合理解决。
- 不为了“统一”再包一层没有语义价值的薄封装，也不为假想需求提前建立复杂框架。

### 面向长期维护

- 修复根因和稳定边界，不依赖易变化的 ID、偶然目录、当前样例或单一版本细节。
- 不在生产路径加入 mock、硬编码假数据、静默 fallback 或伪成功逻辑来掩盖缺失能力。
- 测试中的 mock 只用于隔离真实外部边界，并沿用仓库既有测试方式；优先使用确定性的 fixture、fake 或契约测试，避免把实现细节全部 mock 掉。
- 新增或迁移数据资产时，检查实际内容、体积和用途；示例与场景重建使用保持结构的小型合成实体，真实业务快照通过仓库外的实例配置加载，不把换 ID 后仍可识别的画像当作脱敏。资产已进入 MR 时，核查当前 diff 及待交付提交历史，不能只用后一笔删除提交声称历史已清理。
- 让错误可诊断，兼顾异常路径、资源释放、幂等性、兼容性和并发语义；任务实现模式只处理与当前目标相关的风险。

### 保持架构边界

- 先判断职责属于现有模块还是新的内聚模块。已有模块承担同一职责时扩展它；出现独立职责、复用需求或生命周期边界时再新建模块。
- 不把新文件默认堆在仓库根目录、源码根目录或主入口所在目录；按功能职责归入已有分类目录，缺少合适分类且确有多个内聚文件时再建立简洁的功能目录。不要为了分类创建只含一个普通文件的目录，单文件优先放入最近的已有职责目录并用文件名表达主题；只有框架强制结构、独立包边界或明确的生命周期/权限边界时才例外。
- 将领域逻辑、基础设施适配、配置、提示词、数据模型和入口编排放到仓库已有的对应层级。
- 保持公共 API 小而明确，依赖方向单一；避免循环依赖、跨层访问和把主入口变成杂物箱。

### 贴合仓库风格

- 以选定的仓库参照实现为基准，保持代码表达、模块组织、实现机制和工程流程一致：包括命名与格式、类型与抽象、调用与数据流、状态与错误处理、依赖管理及测试/构建方式。不能只保持表面格式一致，却为同类功能引入另一套实现方式；也不能复用一个接口后，就自行改写其周边范式。
- 一致性不能压过正确性。若既有模式存在已验证缺陷或违反当前仓库规则，按上述仓库调查的证据要求做最小必要偏离；不以“更优雅”或习惯不同为由重造范式，也不为追求一致复制缺陷。
- 控制修改为完成当前模式目标所需的最小完整集合；不夹带范围外清理。
