# 审查意见处理（review-feedback）

用户给出 MR 并说“修改”、处理 CR 或按 review 修改时使用。目标是先判断意见是否成立，再决定回复或改码；review 文案不是修改授权后的事实来源。

## 流程

1. 按[仓库访问](repository-access.md)读取 MR 最新版本、全部评论线程和 review notes，记录 source/target commit；只处理用户指向的 MR 与仍相关的意见。
2. 对每条意见读取被评位置、当前实现、调用方、生产方/消费方、测试和仓库契约，分类为：`valid`、`invalid`、`outdated`、`already_fixed`、`needs_business_decision`。
3. `invalid`：不修改代码；在原线程直接回复反证、适用契约和触发路径为何不成立。未经用户要求不为反驳另发总结评论。
4. `outdated` / `already_fixed`：不重复改；在原线程回复当前版本的修复位置或版本证据。
5. `needs_business_decision`：不猜业务取舍、不修改；在对话中说明缺少的决定，必要时在原线程提出具体待确认项。
6. `valid`：按 implement 流程完成最小完整修复，检查相关入口、调用方、schema/parser、配置、失败路径和测试；验证后提交、同步目标基线并更新原 MR。
7. 推送并回读 MR 最新版本后，逐条在原线程回复：修改位置、行为变化、提交版本和实际验证；确认修复对应原根因后标记 `fixed`。
8. 混合意见逐条独立处理；一条错误意见不得阻止其它正确意见修复，也不得为“统一处理”顺手改错误意见覆盖的代码。

## 回复边界

- 只回复已有 reviewer 线程，不新增重复问题或总结评论；用户另有要求除外。
- 回复前重新核对最新 MR 版本。版本变化导致评论过期时，先映射到当前代码再判断。
- “测试通过”不能代替意见正确性判断；反驳与修复都必须给出代码或契约证据。
