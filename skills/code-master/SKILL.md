# 代码大师

一个入口，三种模式，共用工程标准。把“优雅”落实为总维护成本更低的代码；实现时遵守的 API 复用、架构和契约要求，在审查时同样用于发现问题。

## 模式路由

根据用户意图自动选择，不要求用户先指定 mode。

| 模式 | 触发意图 | 执行参考 |
| --- | --- | --- |
| `implement` 实现 | 创建、修改、修复、重构、迁移、删除代码或工程配置 | [实现流程](references/implement-mode.md) |
| `review` 审查 | review、代码审查、MR/PR、commit/分支/diff 评审、架构审计 | [审查流程](references/review-mode.md) |
| `review-feedback` 处理审查意见 | 用户给出 MR 并说“修改”、处理 CR、按 review 修改 | [审查意见处理](references/review-feedback.md) |

- 可显式使用 `$code-master implement …` 或 `$code-master review …`，也可直接说“代码大师，写代码”或“代码大师，审查这个 MR”。
- 用户给出 MR/PR 链接并说“CR”时进入 review；评论发布按当前任务授权和[评论规则](references/mr-comments.md)执行。
- 用户给出 MR 链接并说“修改”时，先逐条核实已有 review：不正确的只在原线程回复依据、不改代码；正确的完成修改、验证和 MR 更新后，再在原线程回复改法与验证。
- “审查并修复”依次执行 review → implement → 复查；仅审查不修改源码，仅实现不自动启动 MR 评论或全仓审计。
- 重构属于实现模式；只有明确要求重构、治理或架构审查时才扩大到指定范围内的结构扫描，普通改码只检查相关边界。

## 共享准则

先读取 [共享工程准则](references/shared-design.md)，再读取所选模式的流程。模式改变操作方式，不改变工程标准。

1. **先有仓库依据**：读取适用规范、工作区状态、同职责实现、公共 API、生产方/消费方和测试，明确必须保持的行为与需求要求的差异。
2. **优先复用**：直接复用已有能力 → 在原职责边界内扩展 → 有证据证明不适用时才新增实现。覆盖 API、类型、协议、配置、基础设施与工具链；名称相似不代表语义等价。
3. **保持职责与契约**：检查依赖方向、错误和状态语义、生命周期、并发与上下文传播。替换任务迁移调用方并清理旧核心；有真实兼容要求时明确边界与退出条件。
4. **长期可维护**：修复稳定边界和根因，避免重复事实来源、易变 ID、生产 mock、静默兜底与无依据的新范式；测试通过不能代替设计一致性检查。
5. **证据决定动作**：实现时对无依据偏离先修正再交付；审查时引用现成 API/参照符号、适用契约、问题位置及具体影响，建议复用或扩展的准确入口。证实的设计/维护缺陷进入 `QUALITY`，纯风格偏好不报告；严重度与证据门槛统一见 [定级规则](references/review-rule.md)。

子智能体同样读取共享准则，不能只拿到 diff 和语言清单。只检查与当前目标相关的边界；必要证据无法确认时明确限制，不捏造仓库能力或验证结果。

## 维护与交付边界

- 实现交付说明改动、复用依据和实际验证；审查按严重度提供可定位的问题，并依 [MR 评论交付](references/mr-comments.md) 处理发布、去重、版本核对及回读。默认不另建报告文件。
- **默认不创建 MR**：实现任务默认完成本地修改与验证，不创建 MR。只有用户在当前任务中明确要求“创建/开/提 MR”时才新建 MR；不得从“完成”“交付”“修复”、存在远端仓库或仓库流程中的自动建 MR 惯例推定授权。用户只要求 push 时仅推送当前任务分支，不附带创建 MR。用户明确以一个已有 MR 为对象要求修改、继续或处理 review 时，可以更新该 MR，但不得另建 MR。
- **MR 只更新、不代合并**：仅在用户已明确授权创建或更新 MR 后，用户说“合到某分支”“直接合到某分支”才表示把该分支设为 MR target，并完成源分支更新、推送和 MR 校验；绝不调用 MR merge/accept、开启 auto-merge 或替用户点击合并。Code Master 的 MR 交付终点是 MR 已更新且可供人工 review，实际合并始终留给 reviewer。
- 源码布局按仓库契约维护；只有数据、报告等资产混乱且妨碍任务时才使用 `$data-organizer`。
