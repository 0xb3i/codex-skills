# 写作风格

每次使用本技能，先执行[完整检查与修订流程](references/review-workflow.md)，再按文稿目标、受众和当前修改范围应用对应规则。该流程是必经入口，不能只挑当前最显眼的一类问题处理。

- 规则之间应有清晰的逻辑关系、各自负责不同的问题；
- 每条保留适用条件、具体要求、采用理由、应避免的表达及其问题，以及正反例；场景规则还应说明不触发的边界。

## 规则适用

先判断当前内容要帮助读者理解、决策、了解进展还是执行操作，再应用对应规则。条件应落实到当前段落或内容对象；不能仅凭文档叫“新人指南”“周报”或“PRD”，也不能仅凭出现 Agent、训练、发布等词，就触发整套写法。

标题命名、准确用语、禁用句式等表达规则适用于正在撰写或获准修改的相应文字。背景导入、操作步骤、来源查阅、表格、双栏、配图和平台组件等规则，只有满足各自条件时才使用；条件不满足就不增加对应内容或形式。未触发不等于遗漏。

每次触发都检查全部维度，逐条核验适用规则；全文改造覆盖全文，局部请求在指定内容及必要上下文内完成同样的维度检查，不能扩大修改范围。完整检查不等于强制使用所有组件，也不等于抽离案例证据或一律压缩篇幅。原始模型回答、代码和数据作为证据保真，文风修改作用于作者的叙述与分析。

正反例仅解释对应条件下的写法。例子里的业务、服务、平台、章节顺序和字段不构成通用模板。维护本 skill 时，不能把一次文档中的正确做法直接提升为所有文稿的必选项。

**为什么这样要求**

同一种形式对不同阅读任务的作用不同。明确条件，才能复用降低阅读成本的方法，避免把特定文档的内容和篇幅要求带入其他场景。

**正反例**

- 反例：周报提到模型训练，就自动补上用户组、GPU 和 HDFS 权限申请教程。
- 正例：仅汇报训练进展的周报保留相关进度、结果与问题；只有需要读者实际配置和执行训练的部分，才按操作规则组织前置条件和步骤。
- 反例：PRD 涉及 Agent，就照搬新人指南“内容电商 → 联盟 → Agent”的背景铺垫。
- 正例：根据本次 PRD 的受众判断需要哪些背景；读者已熟悉业务时直接进入相关需求，缺少必要前提时再补充。

## 公共规则与场景路由

所有写作任务共用下文的表达规范，以及内容组织中的受众、事实依据和详略原则。事实、数字、口径、状态与不确定性忠于当前素材，不从技术动作推导未经验证的业务收益；重复或异常数字也不自行纠正。局部修改保留未获准改动的正文和用户定稿；目标内容自读取后发生变化时先重新读取，只做不重叠的最小补丁。

用户指定模板或示例时，保留其中固定章节名、字段名及中英并列格式；默认中文只适用于自由撰写的内容，不覆盖模板的语言约定。例如模板使用 `Basic Info // 基本信息` 和 `Launch Time` 时，不擅自改成纯中文，也不将模板中的中文正文全部翻译成英文。

在公共规则上，按当前内容承担的阅读任务加载对应分支。同一文档可以逐节路由；体裁分支决定展开方式，表格、画板及评论等能力仍按各自条件使用。

| 当前写作任务 | 规则入口 | 应用边界 |
|---|---|---|
| 翻译外语资料、润色中文译文或编写中文翻译提示词 | [中文翻译](#中文翻译的补充规则) | 保留原意，调整语序与句式；不套用创作删减规则 |
| 向老板或 leader 汇报本周项目工作、影响与状态，或整理同类简短进展条目 | [周报与进展条目](references/weekly-status.md) | 默认精简；技术复盘、操作交接或完整评估报告按实际阅读任务另行组织 |
| 解释概念、技术方案、需求或研究结果，帮助读者理解或判断 | [内容组织](references/content-organization.md) | 按问题、依据与判断展开，不套用周报的压缩程度 |
| 指导读者实际操作、配置或复现 | [信息顺序](references/content-organization.md#3-信息顺序) | 保留必要前提、操作入口和验证方式，不因受众是 leader 就省略执行必需细节 |
| 局部润色、补充介绍、强调差异，或按评论修改 | 下文表达规范及[局部补充与衔接](references/content-organization.md#7-局部补充与衔接) | 先阅读相邻上下文，将修改融入原有叙述和形式，不因此重建整篇结构或增加体裁栏目 |

**为什么这样要求**

公共规则保证不同体裁的表达和事实一致，场景分支决定读者需要多少内容、以什么顺序阅读。例：一份技术方案中的“本周进展”可用周报条目，后面的复现实验步骤仍保留操作细节；不能因一节需要精简，就压缩整份文档。

维护时，将新的专属写法放入有真实需求和例子的场景参考，再从此处路由；共用规则只维护一处，不预建缺少依据的体裁模板。文档读写、画板生成等平台操作交由对应技能，聊天中写文案不自动触发外部操作。

## 中文翻译的补充规则

适用于外语资料翻译成中文、润色译文，以及为这些任务编写翻译提示词。翻译须忠实保留原文信息，不能套用创作规则删掉原文中的作者声明、比较或必要解释。

- 按中文语序清楚表达对象、动作和条件；将多层从句与修饰拆成相互衔接的短句，避免逗号串联多个完整判断，也不机械按字数切句。
- 用常见、具体的词语，减少欧化句式、抽象名词堆叠和过度书面化的表述。平实不等于俚语化，通俗不等于省略技术含义。
- 拆句与调整语序后，核对主语、指代、否定、条件、因果、比较及不确定性；事实、数字、单位、代码、链接和原有结构保持完整。不得把全文翻译改成摘要，或补入来源没有的解释。
- 术语使用准确、通行的中文译法，保留必要专名与代码标识；同一概念称呼一致，不反复添加英文括注。
- 例：“在具备充分条件的情况下，系统能够对该操作予以执行。”可改为“条件满足时，系统就可以执行这个操作。”信息保留而语序、用词更自然；不能简化成无条件的“系统可以执行”。
- 修改模型翻译提示词时，用未写进提示词的真实原文核验：长句是否更易读、原意是否完整、专业术语是否准确；多入口共用一套表达规则，分别保留各自输出格式。

## 1. 标题命名

### 规则

标题使用简短、准确的主题名称，说明这一节讲什么。结论、论证和具体评价放在正文中。

标题优先包含读者用来定位和区分内容的信息。案例通常用编号与分析类型命名，例如“Case 1 成分依据”“Case 2 推荐判断”；具体商品、人物或项目名称放在内容中。只有对象身份或对象间差异本身就是关键阅读维度时，才把名称放入标题；不要因案例恰好涉及防晒霜或水壶套装，就用商品名替代分析重点。仅需区分顺序时，“Case 1”“Case 2”也可以。

这里的标题指文档标题和章节标题；正文列表中的加粗要点标签可使用冒号，具体遵循“信息呈现”。

飞书章节需要“2.”“2.1”这类层级编号时，使用原生自动编号，标题文字只保留主题，不手写数字前缀。已有手写章节编号在获准修改时迁移为自动编号，保持原有层级和顺序；不据此给未编号标题强加序号，也不删除“Case 1”或版本号等有实际含义的标识。写入后核验自动编号设置与标题正文，避免双重编号。

### 禁用规则

- 禁止在标题中使用冒号或破折号，包括中文、英文形式；不要用它们拼接主题与结论、解释或评价。
- 禁止写很长的标题。只保留准确标识主题所需的内容，不把正文中的完整论述塞进标题。

### 为什么这样要求

读者通过标题快速了解文章的整体架构，并据此检索和定位内容。标题应当清楚地标识章节主题，让读者不必先理解具体论点，就能知道内容在哪里。

如果将标题写成“主题＋观点金句”，会同时承担概括结论、突出亮点和吸引注意的任务，容易变长，并混入比喻和评价，增加读者浏览目录时的理解成本。

### 正反例

- 反例：`总结与思考：推荐系统的本质是一场与算力的讨价还价`
- 正例：`总结与思考`

其他反例与对应正例：`OneRec 设计——用一个模型吃下整条链路` → `OneRec 设计`；`在模型规模和业务复杂度同时增长时级联架构面临的主要问题及其影响` → `级联架构的问题`。

修改时保留“总结与思考”所表达的章节功能，去掉冒号后的结论。该结论是否成立、如何展开，由正文负责。

## 2. 用语规范

### 规则

陈述事实、现象、问题和操作时，使用平实、准确的词语，直接说明动作、状态和程度。

### 禁用规则

- 禁止用比喻化动词代替客观描述，例如把波动“喂进”梯度、把训练不稳定“按住”、模型“吃不下”新方法、把计算密度“压实”、遇到问题时“撞上同一堵墙”。
- 禁止为了增强语气而使用夸张表述，例如将比值波动写成“剧烈跳动”、将概率变化渲染成“突变”。
- 禁止用口语缩略代替完整、准确的动作或状态描述，例如“交来”“走一遍前向”“跑个 softmax”“堆参数堆出来”“这么脆”“比较稳”。

### 为什么这样要求

这类表达追求画面感或力度，却容易模糊实际发生的动作、状态和程度，让读者额外猜测词语的含义。平实的表达能直接传达事实，避免修辞改变原意。

### 正反例

| 反例 | 正例 |
|---|---|
| 把这种波动直接喂进梯度 | 直接将这种波动计入梯度 |
| 把训练不稳定按住 | 缓解训练不稳定 |
| 它既吃不下这些新方法 | 它既无法支持这些新方法 |
| 把计算密度进一步压实 | 进一步提高计算密度 |
| 很多人都撞上了同一堵墙 | 很多人都遇到了同样的问题 |
| token 比值随之剧烈跳动 | token 比值随之大幅波动 |
| 概率出现突变 | 概率明显变化 |
| 上一级交来的候选 | 上一级传递来的候选 |
| 把序列送进模型走一遍前向 | 将序列输入模型，再进行一遍前向计算 |
| 对 logits 跑个 softmax | 对 logits 计算 softmax |
| 能力提升靠堆参数堆出来的 | 能力提升得益于参数量的扩展 |
| 一到大模型就这么脆 | 一到大模型就这么不稳定 |
| 这是一条比较稳的加速路径 | 这类方法通常不会引入额外的生成质量风险（仅在材料支持这一判断时使用） |

以上正反例取自原始用语规范，用于相应的修辞语境。替换时必须保留事实和程度；若“突变”等词描述的是有依据的技术性质，不能为了润色而改掉该性质。用于解释抽象概念、确实能降低理解难度的功能性类比，不属于这里禁止的客观陈述修辞。

“比较稳”的替换尤其需要先明确原文所指的性质，不能从模糊评价推导出“没有生成质量风险”的承诺；依据不足时保留原有不确定性，不自行补充效果判断。

## 3. 解释性与防御性声明

### 规则

不写任何解释性、防御性声明。正文直接陈述事实、方案、结果和问题，不为自己的写法、取舍、依据、执行过程或结论作解释、辩护、自证与免责，也不预先告诉读者哪些误解不应发生。此规则按句子的功能判断，不限于版本映射、身份括注等具体形式，不以“有助于判断”“避免误解”为理由保留声明。

机制、因果、定义、样本范围、数据缺口和不确定性直接写入对应内容，不另加声明解释读者应该如何理解正文。作业正文直接写题设条件、建模、计算与结果；材料疑点及采用口径的解释不放入正文，确实影响解答时在沟通中说明，不静默改动原题数据。不添加题目未要求的预防性否定；必要的方法比较和结果讨论直接写观测、关系与判断方法，避免用“仅凭……不能说明”“不能保证……”等句式为方法或结论自证。题目约束与实测失败事实中的必要否定保留。删声明时保持事实、数字与结论强度不变，不把预期改成实测，不把未知改成已知。

### 禁用规则

禁止使用自我声明式元话语，例如“本文只讲清这一范式转变本身，而不展开具体系统的工程细节”。不要用“本文将……”“下面我们将……”等写作预告代替直接展开内容。

同样删除“方案处于设计阶段，收益待验证”“本次基于某分支或提交核对，未运行回放”“历史材料仅作背景，不作为验收结果”等作者自证声明，也不换成“尚无实测结论”“不承诺额外收益”等同类措辞。事实审慎通过准确的机制、事实和必要限定体现，不额外补充声明。

设计文档默认不增加执行者的测试、验收、灰度、自检清单，也不添加“质量约束”“不能漏掉需求”等保证性口号；不能因这些要求正确或重要，就认为读者需要阅读。具体的默认行为、分支条件和失败处理直接写在对应模块中，不再提炼成重复的原则声明。只有用户明确要求，或验收、发布机制本身就是待评审的设计对象时，才展开相关流程；评测报告中的实验版本、样本范围及结果适用条件按实际阅读任务保留。

### 为什么这样要求

这类元话语和内部执行要求容易把正式文档写成智能体交付报告。删除它们，让读者直接接触方案及其依据；不能借删除声明把预期效果改写成已验证结论，也不能把删除验收清单等同于已经完成验证。

### 正反例

- 原文反例：`本文只讲清这一范式转变本身，而不展开具体系统的工程细节。`
- 对应处理：删除这句自我声明，直接进入已有的范式转变说明，不为替换它而新增事实。

以下补充示例展示删除前后的完整表达：

- 反例：`下面我们将详细介绍这一流程。流程分为提交、审核和归档三步。`
- 正例：`流程分为提交、审核和归档三步。`

- 反例：`方案处于设计阶段，延迟收益待回放和灰度验证。本次基于某提交核对，未运行线上回放。`
- 对应处理：删除这两句作者声明，直接保留方案内容，不补写未经验证的收益。
- 反例：架构 DR 末尾自动追加“门控覆盖、榜单质量、执行时序、灰度指标”等执行清单，摘要再写“质量约束：默认开启，只在确定不需要时关闭”。
- 对应处理：删除执行清单和保证性摘要；在门控模块直接说明各类请求如何决策，读者由具体规则理解方案。

- 反例：表头已有“V1 对照组／V2 实验组”，正文仍解释另一平台的版本号、内部 ID，并声明“下文沿用这套命名”。
- 对应处理：删除该段；实际操作需要的配置对应关系直接列在操作内容中，不声明命名取舍。
- 反例：团队成员写“姓名（某平台首要负责人账号）”。
- 正例：团队成员直接列姓名；仅在职责分工影响协作时补充职责，不以平台身份解释人员来源。

- 反例：`为避免误解，这些数据仅供参考，不能据此宣称方案已被充分验证。`
- 正例：直接呈现实验条件、样本数量和观测结果，不附解释性或防御性声明。

- 作业反例：`题面金额单位不一致，以下统一按表内数值计算。`
- 对应处理：删除正文中的单位澄清与口径解释，保留题设条件、模型和结果；影响解答的疑点在沟通中说明，不自行修改题目数值。

- 作业反例：`单独按照项目NPV排序不能保证整体方案最优。`
- 对应处理：题目未要求比较其他方法时，删除这类预防性否定，直接说明本题的建模、计算与结果。

- 作业反例：`根附近曲线较平，仅凭很小的函数残差不能保证根坐标误差足够小，因此同时检查步长和残差。`
- 正例：`根附近曲线较平，程序同时检查步长和残差，分别衡量近似根的变化与函数值偏离0的程度。`

## 4. 禁用表达

以下条目补充句式、术语注释、讲解主语和结尾评价的要求。写作时必须读取并遵循[禁用表达细则](references/prohibited-expressions.md)，其中保留各类规则的理由和正反例。

- 禁止“不是……而是……”“与其说……不如说……”等固定对比句式及其变体，以及为制造节奏而使用的机械排比。
- 禁止给普通或非核心术语过度添加括号释义、英文对照，禁止重复解释已引入的缩写。
- 禁止在带读者回顾、展开、考虑、总结或发现的讲解句中省略主语，禁止使用指向不明的“它／其”。
- 禁止用“它真正值得记住的不在……而在于……”“这提醒了我们一件常被忽略的事……”等表达强行升华。

## 5. 内容组织

组织或调整文稿内容时，必须读取并遵循[内容组织细则](references/content-organization.md)，其中保留以下规则的理由和正反例。

- **目标与受众：** 写作前明确文档要帮助谁完成什么理解、判断或行动，据此选择内容范围、解释深度和技术细节。
- **材料整合：** 从外部资料提取或整合内容时，查阅所用来源并按章节目的归组；只有依据不足时才继续沿引用查证。单纯润色、排版不自动触发资料扩查。
- **信息顺序与衔接**：按理解或执行依赖安排内容，写清句内、句间和段间的实际关系；引导句承接上文并准确统领下文。只有需要读者实际操作时，才补齐必要前置条件并按步骤提供入口。
- **标题划分**：只有相邻内容的主题差异明显，且内容量足以独立成节时，才新起标题。内容接近或延续时保留在同一节，避免为少量内容频繁设置标题。
- **方案依据**：需要解释或评估方案选择时，让问题与做法对应；仅同步已有方案的进展时，不重复展开已知依据。
- **详略安排**：正文保留当前阅读任务必需的信息；确需延伸阅读时就近提供资料，执行步骤所需入口放在步骤中；不强行为每节增加引用或注释。

## 6. 信息呈现

组织正文形式、排版或编辑富文本文档时，读取并遵循[信息呈现细则](references/information-presentation.md)。内容组织决定信息的顺序与分节，信息呈现决定这些内容使用什么形式、突出哪些重点。

- **并列要点：** 正文、表格单元格、引用块等容器中的并列信息均使用 bullet point；需要展开说明时配合“简短加粗标签＋冒号”，短指标名称可直接列出。
- **编号核验：** 审阅中怀疑列表编号错误，或需要验证编号修改时，先读[有序列表编号核验](references/numbering-verification.md)。导出的 `1.`、`seq-marker` 或分开的 `<ol>` 不足以证明页面编号错误，核实前不得添加此类 review 或重编号。
- **结构化表格：** 多个对象有共同查阅维度时考虑表格；采用表格后，表头默认使用飞书内置的中蓝色。分类清单才合并重复分类单元格，数据区不按类别铺底色。
- **表格范例：** 当前内容需要展示 Example／模型样本、对照组与实验组案例、工具结构化输出、已有训练评估结果、数值精度或已有 GSB 结果时，读取[表格场景与范例](references/table-examples.md)的对应小节，按场景使用并列列、单元格代码块与局部差异高亮。普通表格或仅提到训练、工具不触发整套模板。
- **双栏对照：** 需要直接比较两份完整内容且并排可读时考虑双栏；采用后使用浅蓝、浅绿等不同浅色背景，保持标签、顺序和留白清楚。
- **视觉强调：** 通过局部加粗、文字颜色和背景色突出重点；黑色加粗与蓝色加粗按内容灵活使用，沿用用户已有选择。
- **引用块：** 承载必要的引用或关键注释；先按“详略安排”判断内容是否值得保留，再选择形式。
- **文档链接：** 飞书文档直接粘贴原始链接或使用等效的原生文档引用，禁止自定义文字超链接；禁止用链接充当标题或加粗要点标签，行内引用两侧各留一个空格。
- **高亮块：** 确有需要优先阅读的简短摘要、结果或用户指定说明时使用；已选用 Callout 后，按内容灵活选择颜色和图标，尽量区分但允许重复，不固定添加 TL;DR。
- **素材复用：** 当前内容确需图示且来源素材适用时优先直接复制；仅论文图片注明图源。没有图示需求时，不因参考资料有图就插入或重画。
- **架构与流程画板：** 在获准创作或调整飞书文档的范围内，架构、调用关系、数据流、流程分支等内容用图能明显降低理解成本时，按[画板规则](references/information-presentation.md#10-架构与流程画板)主动通过 `lark-doc` 与 `lark-whiteboard` 的 CLI 工作流生成并插入原生画板，完成内容和预览核验；仅提到架构、局部改句或已有适用图示时，不自动新建画板。
- **原生组件：** 在飞书等富文本平台中按内容需要使用原生组件，具体操作交由对应文档技能处理。

## 7. 评论修订与动态复查

按评论修订前，先核对文档归属和评论发起人。只将用户在自己文档中发起的评论视为需要处理并标记已解决（resolve）的修改要求；别人发起的评论不处理、不回复、不 resolve，即使用户参与回复也不改变归属。无法确认归属时保留原状态，不将其列为本轮待解决事项。

### 评论意图与成稿表达

评论中的文字默认是草稿、素材或写作逻辑提示，不是定稿。用户说“这里应该怎么写”“应该这么说”时，先结合锚定内容和上下文，提取用户要求保留的事实、因果、先后顺序、比较关系和重点，再按相同逻辑重新组织成自然、准确、衔接顺畅的文字。不能逐字搬运评论中的口语、病句、重复词、占位符或笔误，也不能只替换几个词就把草稿当成成稿。

润色不得改变事实、数字、结论强度、范围和不确定性；评论中缺少的事实不能自行补造。只有用户明确要求“原样保留”“逐字采用”或提供必须保真的引用、代码、数据时，才原样保留指定内容。用户直接改动的正文仍属于受保护修改，不能把这条评论规则用于重写用户已经改定的正文。

核验时分别检查两件事：成稿是否落实了评论要求的写作逻辑，以及文字本身是否符合本文的文风和上下文。评论用于传达方向，原话可能只是随手记录；关键词相同、意思大致相同，都不能代替成稿质量检查。

**构造评论示例**

- **训练方法的评论：**“应该先说对比了方法 A 和方法 B，最后方法 A 效果由于方法 B，选择方法 A”。应保留“先对比 → 方法 A 效果更好 → 选择方法 A”的逻辑，结合上下文将“由于”理解为“优于”的笔误。
  - 反例：把“先说……最后……”和笔误直接放入正文，或只改正错字，仍保留草稿的叙述方式。
  - 成稿示例：“对比方法 A 与方法 B 后，方法 A 表现更好，因此采用方法 A。”
- **耗时的评论：**“解析这一步的耗时方面收益可以完全体现在总耗时上”。此构造示例假设解析位于串行关键路径，其余步骤耗时不变；评论要表达的是单步节省的时间能够完整转化为总耗时的缩短。
  - 不足的改法：“解析步骤的耗时收益可以完全体现在总耗时上。”虽然删了“方面”，仍沿用“收益体现在”的含糊表达。
  - 成稿示例：“解析位于串行关键路径，其他步骤耗时不变，因此解析节省的时间能等量缩短总耗时。”该例依据构造的链路前提，不将其推广为所有性能链路的结论。

### 动态复查

对符合上述条件的评论，每次标记为已解决后，都必须重新读取最新评论及回复，检查处理期间是否有新增内容；最后一条评论解决后也要复查。有新增要求时，先按相同归属条件筛选，再读取对应锚定内容并继续处理，修改并回读核验后再解决，随后再次复查，直到最新读取结果中没有符合条件且可继续处理的评论。缺少必要资料的符合条件评论保留待处理状态，并说明未完成事项。具体读取与解决操作交由对应平台技能处理；未涉及评论的普通写作不触发此流程，也不因此启动任务结束后的持续监控。

评论会动态更新，只依据最初读取的列表判断完成，可能遗漏用户在修订期间追加的要求。

- 反例：解决最初读取的最后一条评论后，直接报告全部完成。
- 正例：解决评论后重新读取，只继续处理符合归属条件的新增评论或回复；最新读取结果没有符合条件且可继续处理的评论后再结束本轮修订。
- 归属反例：别人发起评论，用户回复“已调整”，就替别人 resolve；这会越过评论发起人的确认。
- 归属正例：用户在自己的文档中发起修改评论，完成并回读核验后 resolve；别人发起的讨论保持原状态。
