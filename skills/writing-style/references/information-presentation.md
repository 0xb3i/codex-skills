# 信息呈现细则

列表、表格和双栏负责组织信息关系，视觉强调负责标出阅读重点，引用块和高亮块区分不同内容的阅读作用，原生组件负责在目标平台实现这些形式。各规则可以组合使用，例如在表格单元格内列点，并对其中的关键结果加粗和着色；不要求每篇文章使用全部形式。

## 1. 并列要点

**适用条件**

当前内容中确有多个需要分项阅读的并列要点时适用。连续解释、因果推导不因提到多个概念就拆成列表；是否编号取决于执行顺序。

**规则与禁用内容**

同一主题下存在多个相对独立、彼此并列的问题、原因、措施、指标或资料时，使用 bullet point 分项表达。判断依据是信息之间的关系，适用于正文、表格单元格、引用块和高亮块等容器；不要只在正文段落中使用列表，也不要因为内容已放进表格，就用分号或顿号把多个独立指标挤在一行。

需要展开解释的要点以“**简短标签：**”开头，随后说明具体情况、依据或影响。同一组同类条目的标签和格式保持一致，例如并列的“**类目划分：**”“**商品数量：**”，不要仅给第一项加标签。只有指标名称或简短资料条目时，直接逐项列出即可，不必为每项重复添加标签、冒号或解释。同一指标的名称与限定口径保留在同一条，不能为了列点拆散其含义。

每项围绕一个明确的点展开，同一问题的现象、原因和影响保留在该项中。标签应概括当前条目的职责、机制或关键变化，让读者仅扫描标签就能区分各项；避免只有“问题一”“问题二”等编号，也避免用“数据准备”“相关处理”等过于宽泛的名称掩盖本项要说明的具体变化。标签详略由当前比较维度决定，通用名称已足以定位时无需扩写。

条目内的信息按该条目的说明目的和职责归属组织，不因某句话提到同一节点，就把它放在该节点的任何条目下。决策条件和触发后的执行行为放在负责该决策的条目中；介绍输入压缩时，说明各环节的输入如何减少，区分匹配节点输入与后续模型输入。同一机制影响多个条目时，可分别说明与当前目的相关的行为或结果，不机械搬走所有相关事实，也不在两项重复整套执行说明。不要将多个独立问题压进一个长段落，也不要把连续推导机械拆成列表；操作步骤按执行顺序编号。

标签属于正文，不增加目录层级，可以使用冒号。是否需要另起章节仍由“标题划分”决定。多个对象具有共同字段且需要对照时，按下一条判断是否更适合表格。

**为什么这样要求**

分项和标签能直接呈现信息边界。读者可以先扫描要点，再阅读解释，减少自行从长段落或单元格中拆解和归纳的负担，同时避免增加过多章节标题。表格对齐对象与维度，列表区分维度内部的并列条目，两种形式可以同时使用。

## 2. 结构化表格

**适用条件**

多个对象有共同字段，且读者需要逐项查阅或对照时，才考虑表格。表头配色只在使用表格且目标格式支持背景色时适用；合并分类单元格只适用于确有重复分类的清单，不要求把所有周报或 PRD 表格都做成工具目录。

当前表格需要展示 Example／模型样本、对照组与实验组案例、工具结构化输出、已有训练评估结果、数值精度或已有 GSB 结果时，再读取[表格场景与范例](table-examples.md)中的对应小节；其他表格不套用这些列和小数位。

**规则与禁用内容**

信息密度较高，且多个对象具有共同的比较或查阅维度时，优先考虑表格。用行区分对象，用列区分维度；层级、指标、适用范围、评分标准和权重等信息应各有清楚的位置。

中文说明文档的表头统一使用准确的中文业务名称，便于读者直接理解列的含义；ID、MCP 等通用缩写可保留。例如采用“榜单类型 ID”“榜单类型名称”“排序指标”，避免同一行混用“榜单”、`board_type_id`、`board_value` 这类不同命名方式。确需对照接口或底表时，在已有字段说明中保留准确映射；代码、Schema、数据字典的字段名及枚举值保留原文，不为中文化改写真实标识，也不无条件给每个表头追加英文。

较长的评分标准可以保留在单元格中，通过分段或列表组织内部层次，并为说明列分配足够宽度。单元格内有多个并列指标、条件或要点时，遵循“并列要点”规则列出，不以文字长短决定是否列点。不要因标准较长就退回多层嵌套列表，也不要为缩短表格而删去关键条件。没有共同维度的连续论述不必强行制表，避免将整段文章塞进单列表格。

比较方向保持一致，列名明确对象和单位。表头文字统一左对齐，不随数据列改为居中或右对齐；数据区的数值右对齐，状态可居中，说明左对齐并顶端对齐。表头固定起点便于扫描列名，数据区按内容对齐便于比较；例如“控制组／实验组”表头左对齐，下方得分仍右对齐，避免把整列的对齐设置同时套到表头。平台不支持时优先保留清楚的行列对应。只有理解表格需要而上下文尚未交代时，才在表旁补充读表目的、来源、时间、口径或样本范围。表后解释影响判断的关键差异，不逐格复述。精度、差值和空值符号按[小数位与差值](table-examples.md#3-小数位与差值)处理，既有源值优先。

表头默认使用飞书内置的中蓝色背景，表头文字保持清晰可读；用户已经设置具体颜色时，沿用其选择。本次用户选择的中蓝色色值为 `rgb(225,234,255)`（`#E1EAFF`），不要替换成更浅的 `rgb(240,244,255)`。不要默认采用浅灰表头，也不要把表头底色扩展到整张表。这里约定的是表格 header，不据此将所有章节标题统一改成蓝色。

按信息归属组织内容，保持读者完成当前查阅所需的信息就近完整。已有表格中，定义、公式和规则属于某个比较对象或维度，且是理解该项所必需的内容时，保留在对应单元格内；长内容先用单元格内的 bullet point、加粗标签、原生公式和合理列宽改善排版。不能仅为缩短表格或降低单元格字数，就把内容抽到表外，让读者重新拼接对应关系。仅在用户明确要求拆分、内容是多个对象共用的说明，或属于非当前查阅必需的详细推导时，考虑单独组织，并在原处保留必要结论和明确指引。判断调整是否有效，要看读者能否就近理解该项、是否减少跨位置查找，不能只看表格是否变短。

支撑当前论据的案例资料属于正文证据，不能按外部 Wiki 或飞书参考文档的方式处理。评测案例的问题、商品资料、两组回答和差异分析应放在一起，让读者当场核对；不能仅为压缩正文，就用节选替换已有完整案例，再把完整资料集中到文末或另页，要求读者跳转。例：分析卖点如何改变推荐理由时，商品描述、翻译及模型回答就近并列，优先改善列宽、列表和局部高亮。用户明确要求节选或分离原始数据时，再按其范围调整。

工具目录、能力清单等按类别分组的表格，将同类条目相邻排列，纵向合并分类列中重复的单元格，每个类别只显示一次。对象名称、功能等明细仍各占一行，不合并不同对象的信息。数据区保持无背景色，用合并单元格和表格边界区分类别，不再给各组铺不同底色；蓝色表头继续保留。必要的关键结果强调仍遵循“视觉强调”，双栏布局的背景约定不受影响。

**为什么这样要求**

固定列让读者能沿同一维度比较不同对象，也能沿一行查全某个对象的信息。大量嵌套列表会反复出现字段名称，使读者需要上下寻找对应关系；表格将这些关系直接对齐。中蓝色表头标明字段名称，与数据区形成清楚边界，也符合用户偏好的配色。

分类单元格合并后，既减少重复标签，也明确标出一组条目的归属；无需再用成片底色重复表达同一分组关系。

**正反例**

反例：每个指标都使用一组多层 bullet point，分别列出层级、适用域、评分标准和权重；长评分标准再继续嵌套子列表，多个指标之间难以对照。

正例：将共同字段固定为列。以下构造两个文本处理指标，展示组织形式：

| 层级 | 指标 | 适用域 | 评分标准 | 权重 |
|---|---|---|---|---|
| 格式 | `format_pass` | 文本抽取 | 校验输出能否解析为 JSON，且包含规定的字段；此构造规则将格式不合格的样本单独列为无效样本，不纳入内容评分。 | 单独报告 |
| 内容 | `entity_precision` | 文本抽取 | 在格式合格的样本中，正确抽取的实体数除以全部抽取的实体数；没有抽取实体时记为 n/a，并单独报告此类样本数。 | 单独报告 |

更复杂的 Query 评分标准可以在对应单元格内按相关性、粒度、规范性和多样性分项，表格外层仍保留统一的指标结构。

- 表头反例：新建指标表时仍使用浅灰色表头，忽略文档中用户已设置的蓝色样式。
- 表头正例：“环节／主要指标／观察重点”三列表头均使用飞书内置中蓝色背景，数据区保持普通底色；保存后核验实际背景样式。
- 分类反例：MCP 工具表在每行重复“选品”“创作”，或合并分类单元格后仍将两组数据分别铺成蓝色、绿色背景。
- 分类正例：MCP 工具表保留“用途／MCP 工具名／功能”三列及中蓝色表头；选品工具连续排列，共用一个纵向合并的“选品”单元格，创作工具同样处理；名称和功能逐行对应，数据区无底色。
- 单元格归属反例：为缩短榜单表格，把回购公式及其四项指标定义移到表后，回购榜单元格只剩“回购指数”。
- 单元格归属正例：回购公式和指标定义保留在回购榜的排序逻辑单元格内，定义用 bullet point 分项，标签加粗，读者在这一行即可理解计算口径。
- 方向反例：同一张表在不同指标行交换 Base 与 SFT 的位置，差值又未说明减法方向；读者无法沿列比较。
- 方向正例：各行保持“Base／SFT／变化”顺序，注明变化为 SFT 减 Base，数值按列对齐；只说明影响当前判断的差异。

## 3. 双栏对照

**适用条件**

确需直接对照两份相对完整的内容、且目标平台能清晰并排呈现时适用。出现两个对象不自动触发双栏；两侧配色要求仅在选用双栏后生效。

**规则与禁用内容**

需要直接比较两份相对完整的内容时，可以使用双栏布局，左侧放一个对象，右侧放另一个对象。例如对照组与实验组配置、修改前后的回答、两个方案的流程图或界面截图。

两侧使用明确、简短的标签，并在同一篇文档中保持对象的左右顺序一致。尽量按相同维度和顺序组织内容，让对应部分处于相近位置；公共背景放在双栏之前，共同的差异分析可放在之后，避免两侧重复说明。栏宽按内容需要分配，以文字、代码和图片清晰可读为准，不为并排而过度压缩内容。

双栏应有清楚的背景分区：每栏使用独立的浅色背景包裹本栏内容，默认两侧使用不同颜色，例如左侧浅蓝、右侧浅绿，并保留栏间留白和适当内边距，让读者一眼看清各段属于哪一侧。避免使用浅灰背景造成整体观感灰暗，也不要只把文字左右摆放在同一白底上，或用一整块连续底色覆盖两栏。配色保持浅淡，保证文字清晰；用户已有明确配色时沿用其选择。这里的底色用于区分对象，不表示优劣，局部指标着色仍遵循“视觉强调”。

背景色必须实际写入并保存到文档组件。核验时读取保存后的样式，或在光标移开、取消选中后检查显示效果；不要将 hover、focus 或选中态产生的临时底色当作已设置的背景。

双栏适合保留两份内容各自的段落、代码或图示结构，便于读者直接对看；需要逐项查阅多个对象的统一字段、指标或评分标准时，优先考虑结构化表格。不要仅因出现两个对象就强制双栏，也不要将无关内容为了排版对称放在一起。

**为什么这样要求**

将待比较内容放在相邻位置，可以减少上下滚动和记忆前文的负担。明确的标签和对应顺序帮助读者定位差异，同时保留每个对象完整的上下文。不同的浅色背景与栏间留白进一步标明内容归属，在区分两侧的同时保持明亮的页面观感。

**正反例**

- 反例：先放完整的对照组配置，中间插入大段说明，后面再放实验组配置；读者需要反复上下翻找才能确认改了什么。
- 正例：左栏标注“**对照组**”并放置配置代码块，右栏标注“**实验组**”并放置相同字段顺序的配置代码块。构造示例中，两侧的 `include_summary` 分别为 `false` 和 `true`，对应字段并排呈现后，差异可以直接看到。
- 背景反例：“节点评测”和“端到端评测”仅靠左右摆放区分，文字与页面同为白底；或两侧统一使用浅灰底，缺少颜色区分且页面观感灰暗。
- 背景正例：“节点评测”使用浅蓝背景，“端到端评测”使用浅绿背景，各自包住标题、要点和资料链接，中间保留白色间隔。

此构造示例只说明配置对照的排版。飞书编辑时使用原生分栏组件，具体语法按“原生组件”规则读取当前文档工具说明。

## 4. 视觉强调

**适用条件**

当前内容确有需要优先注意的关键信息时使用。指标改善着色还须有对比依据且目标格式支持；没有关键变化时不强行着色，也不要求所有文稿都有指标结果。

**规则与禁用内容**

展示评估结果或指标时，选择对结论重要的信息进行局部强调。有依据的明显正向改善，可以使用浅绿色背景并加粗关键结果或变化幅度；判断改善方向时结合指标含义，例如耗时降低也可以是正向结果。

正文加粗可以保持默认黑色，也可以配合蓝色文字突出重点；按内容灵活使用，优先沿用用户已设置的强调方式。不把全部加粗统一改蓝，也不规定某一类文字必须固定用黑色或蓝色。蓝色文字用于阅读强调，不自动表示指标改善；表头背景色遵循“结构化表格”的约定。

同类信息的强调方式保持一致。保留对比起点、指标名称和必要口径，使重点能够被正确理解。不要整表、整段或所有数值同时加粗着色，也不要通过弱化重要负向结果来制造单向结论。颜色和加粗只改变视觉优先级，不提高事实强度；统计显著性仍需原始材料支持。

**为什么这样要求**

读者扫描结果时，需要快速识别关键变化。局部强调能降低寻找重点的成本；过多着色会削弱层次，脱离指标含义的配色则可能误导判断。

**正反例**

- 反例：将整个结果表统一设为绿色背景并全部加粗，辅助数据与核心指标没有视觉区别。
- 正例：在构造示例“模型 A 的准确率由 0.7000 提升至 **0.8400（+20.00%）**”中，仅对加粗部分使用浅绿色背景，保留起点和指标名称的普通样式。这些数值为构造材料，不据此宣称真实改善或统计显著。
- 文字颜色反例：看到一处蓝色加粗，就把全文所有黑色加粗一并改蓝。
- 文字颜色正例：沿用用户对“使用 → 选品 → 发文 → 动销”设置的蓝色加粗（示例色值 `rgb(36,91,219)`），其他位置根据内容保留黑色加粗。

## 5. 引用块

**适用条件**

已有必要引文、关键注释或延伸资料，且需要与主论述区分时使用；同一步骤需要并列提供多个操作入口时，也可按“详略安排”用引用块承载入口列表，紧邻对应说明。常规正文和操作指令不自动放进引用块，也不为使用组件而新增资料。

**规则与禁用内容**

先按“详略安排”判断引用或注释是否必要。确需引用原文、保留关键澄清或提供有实际查阅用途的资料时，再使用引用块区分其与主论述的关系；引用块不构成保留冗余说明的理由。原文引用标明来源，必要的补充说明用“说明”等标签明确性质，转述不要伪装成逐字引文。

对紧邻正文、确有必要保留的评估口径、例外条件等短注释，优先使用原生引用块，并以加粗的“注：”开头，后接普通正文；字段名、代码标识保留行内代码格式。已有准确标签如“评分说明：”可沿用，不把普通正文、核心结论或纯资料链接一律改成注释。

不要将无关段落全部放进引用块，也不要把理解主论述必需的前提隐藏成边注。资料是否需要用途说明，按“详略安排”判断；名称和上下文已清楚时，只保留引用即可。

**为什么这样要求**

引用块能区分主论述和来源、注释，减少补充材料对阅读主线的干扰，并让读者知道哪些内容是在引用、哪些内容属于说明。

**正反例**

- 反例：在结果分析段落中连续插入来源、评分口径和链接，读者难以区分结果与补充说明。
- 注释正例：判定标准后紧接原生引用块：

> **注：** 在此构造的实体抽取评测中，只比较 `entities` 内的实体，`explanation` 不参与实体准确率；格式是否合格单独报告。

这条注释用于澄清当前评测的具体口径；没有相应评测内容时不添加，也不把整段文字全部加粗。

- 正例：构造结果表中的“无效样本”若容易被误读成内容错误，可用引用块简短说明判定机制；正文已解释时无需重复：

> **评分说明：** 此构造规则将无法解析的输出单独计为无效样本；实体准确率只统计格式合格的样本，同时报告无效样本数。

## 6. 高亮块

**适用条件**

确有需要优先阅读、可独立理解的简短结论或摘要，或用户明确要求用 Callout 呈现某段说明，且平台支持高亮块时使用。简短周报、单项需求或正文已足够清楚时，不额外制造 TL;DR。以下配色和图标要求仅在已选用 Callout 时生效。

**规则与禁用内容**

需要让读者优先看到 TL;DR、核心结论或重要结果摘要时，使用 Callout 高亮块。内容应简短、自足，直接给出结论和必要限定；详细论证保留在正文。

高亮块强调一组信息的阅读优先级，局部加粗与背景色强调具体词句或数值。不要让每段都有高亮块，不把整节内容搬进高亮块，也不使用“本文将介绍”等写作预告代替摘要。

颜色与图标根据当前内容和用途灵活选择。Callout 使用浅色背景铺色，搭配同色系、比背景略深且可辨识的边框；例如浅蓝底配蓝色边框、浅橙底配橙色边框。浅色底保持文字清晰，同色系边框明确块的范围，避免只设背景而遗漏边框，或使用不协调的异色边框。平台支持时同时设置并核验背景色与边框色，不固定套用同一种配色和图标。文中不同用途的 Callout 尽量有所区分，但不强制逐个唯一；同类内容重复使用相同样式也可以。示例配色不构成固定映射，不为避免重复而使用不贴切的图标或颜色。

**为什么这样要求**

读者可以先获取核心结果，再决定深入阅读哪些部分。高亮块过多或过长，会失去快速概览的作用。

贴合内容的颜色和图标能帮助读者辨认不同说明；机械统一或强制不重复都会让样式选择脱离内容。

**正反例**

- 反例：将完整的训练过程、全部评分指标和结果逐项复制进一个很长的 Callout，开头仍是“下面将介绍训练效果”。
- 构造正例：在 Callout 中用“**结果摘要：**”引出两个原生 bullet point：
  - 模型 A 的准确率由 0.7000 提升至 0.8400（+20.00%）。
  - 同一测试环境中，解析步骤耗时由 2.4s 降至 1.8s。

分域得分、评分口径和分析保留在后续正文或表格中。高亮块内部同样遵循“并列要点”的规则。

- 样式反例：所有 Callout 都固定用浅蓝色加 💡；或为了保证图标不重复，给测试说明选择无关的庆祝图标。
- 样式正例：本篇中，入门信息可用浅蓝底与蓝色边框配 📖，示例可用浅橙底与橙色边框配 💡，测试说明可用浅绿底与绿色边框配 🧪；另一篇根据具体内容重新选择，同类说明允许复用样式。

## 7. 素材复用

**适用条件**

图像或画板能帮助理解当前主题，且任务允许增补或调整这些素材时适用。仅因来源有架构图或截图，不构成往周报、PRD 等文稿插图的理由；复制失败处理仅在实际需要复制原生画板时触发。

**规则与禁用内容**

当前内容需要图示时，检查参考资料中的相关图像、架构图、界面截图和画板。已有素材能清楚解释当前主题、适合受众且内容口径明确时，优先直接复用到主文档，配合必要的文字说明。仅论文图片注明图源；其他素材不额外添加“图源”“截图来源”或“复用自某文档”等介绍。用于深入阅读的资料链接仍按正文需要保留。仅放参考链接不能代替正文所需的图示；不要因为正在重写文章，就默认所有图都要重新绘制。

优先通过目标平台支持的原生资源复制方式保留图片质量和画板的可编辑性，不修改来源文档。按正文需要调整展示尺寸和位置，保留必要图例、版本及规划项说明；来源图包含历史设计时，明确其与当前状态的关系，不把规划内容描述成已上线能力。若没有合适素材，或现有素材无法满足准确性与阅读要求，再补绘或改编。

原生画板复制失败时，如实报告失败，在交付回复中提供源画板链接和插入位置，交由用户手动复制；未经用户明确要求，不得用截图、导出图或重绘图替代原生画板，也不得声称复制已完成。这不影响直接复用参考资料中原本就是图片的素材。

**为什么这样要求**

参考资料中的图示往往已经整理了完整关系或真实界面，直接复用能减少重复制作和转述遗漏，也让正文与依据保持一致。图旁优先说明读者需要理解的内容，避免重复介绍内部素材的出处；论文图源则用于查证研究依据。素材是否适用取决于内容和受众，不能仅凭“自行绘制”或“来源现成”判断质量。

**正反例**

- 架构反例：参考 LR 已有清晰完整的架构画板，却另画一张信息更少的流程图，只在文末附上 LR 链接。
- 架构正例：在新人指南的架构部分复制 LR 2.0 的原生画板，说明图中规划项、历史节点的口径，再用正文解释新人需要理解的主流程，无需另写内部图源。
- 图源反例：在内部 App 截图旁写“截图来源：某 LR”，图注中又写“复用自某 LR”。
- 图源正例：内部截图仅标注“达人助手首页”；引用论文架构图时注明论文名称及链接。
- 失败处理反例：原生画板复制失败后，擅自插入高清导出图，并将素材复用任务标记为完成。
- 失败处理正例：说明原生画板复制失败，提供源画板直达链接和主文档中的插入位置，留给用户手动复制。
- 界面反例：介绍 Agent 的使用形态时仅写文字，或重新制作示意界面，忽略参考资料中的真实 App 截图。
- 界面正例：直接复制 LR 2.0 的“达人助手”截图到体验部分，保留原图内容，调整显示尺寸，图注说明界面内容。

以上是产品指南素材复用的构造场景，用于说明复用原则。实际编辑应从用户提供或项目指定的资料中读取素材，不预设某份文档。

## 8. 文档链接

**适用条件**

内容实际包含引用或资料入口时适用。原始链接／原生文档引用要求针对飞书文档；平台关联与组件验证要求只在编辑相应富文本文档时触发，不据此为没有引用的内容新增链接。

**规则与禁用内容**

引用飞书文档时，直接粘贴原始文档 URL，让平台识别为原生文档引用。禁止写成 `[文档名称](URL)`、HTML `<a>` 或其他自定义文字超链接，也不要把原始 URL 包在代码格式中。此规则适用于正文、列表、表格单元格和引用块中的 Docx、Wiki 等飞书文档引用。

通过工具编辑飞书时，使用与粘贴原始链接等效的原生文档引用组件，并保留已有原生引用；回读验证引用类型和目标文档，不能只检查文字能否点击。涉及原始链接中的定位锚点或参数时保留其定位含义，无法保留时直接贴完整原始 URL，不擅自裁剪。

禁止用链接充当文档标题、章节标题或列表中的加粗要点标签，也禁止通过给链接加粗来模拟标题。标题和标签使用无链接的文本，引用放在后面的说明句或资料入口中。看板、代码仓库等非飞书文档网页仍可使用普通文字超链接。

行内引用与前后文字之间各留一个空格。空格放在引用外部，不修改 URL，不重复插入多个空格；位于段首或段尾、没有相邻文字的一侧无需补空格。

**为什么这样要求**

自定义文字超链接可能无法被飞书识别为文档引用，导致“本文引用”不显示对应文档。原始链接经平台识别后形成的原生引用能保留文档关联。

链接自带的蓝色容易与蓝色加粗强调混淆。将标题标签与引用入口分开，并在行内保留适当留白，能帮助读者区分内容层次和资料入口。

**正反例**

- 飞书引用反例：`参照 [产品体验指南](文档原始URL) 完成产品体验。`
- 飞书引用正例：直接粘贴用户提供的产品体验指南原始链接，由飞书生成原生文档引用；通过工具编辑时直接写入对应原生引用组件。
- 留白反例：`参照〈原生文档引用〉完成产品体验。`
- 留白正例：`参照 〈原生文档引用〉 完成产品体验。`
- 标题反例：`**[GPU 看板](URL)：**查看模型服务的 GPU 使用情况。`
- 标题正例：`**GPU 资源：**通过 [GPU 看板](URL) 查看模型服务的 GPU 使用情况。`

以上代码格式与“〈原生文档引用〉”仅用于展示规则，实际正文不保留代码格式或占位文字。非飞书网页示例中的 URL 使用对应真实地址。

## 9. 原生组件

**适用条件**

在支持对应组件的平台中编辑富文本文档，且内容关系确实需要该组件时适用。纯文本或 Markdown 不要求模拟不存在的组件；某组件不可用时，不反过来扩充内容。

**规则与禁用内容**

在飞书等富文本平台撰写或编辑文档时，根据内容关系和阅读用途，灵活使用平台支持的原生表格、分栏、引用块、Callout、行内背景色、加粗及图示等组件。形式可以组合，不限定为纯段落或纯 bullet point，也不为使用组件而增加无关内容。

展示比例、分式等数学关系且普通文本难以阅读时，优先使用原生公式；inline code 用于代码和标识，不用来包裹整段中文计算口径。公式用清楚的短名称，完整限定条件紧邻公式保留，原属表格的公式与口径仍在同一单元格。列表和单元格内的公式默认使用紧凑行内样式，字号与相邻正文协调；不要默认使用展示型大分式（如 `\displaystyle`），导致公式突兀或明显撑高行距。例：回购率用“回购去重用户数／购买去重用户数 × 100%”的原生分式，同条说明统计周期及“购买过该商品至少一次”的口径，避免把整句长中文塞进分子、分母。简单加减关系或普通定义用自然文字即可，不因提到指标就强制 LaTeX；写入后检查分式、换行和单元格边界的实际呈现。

实际编辑飞书时，联动 `lark-doc` 技能及其 CLI 参考，按所用组件读取相应操作说明；涉及画板等资源时按文档技能路由处理。组件语法和能力以当前工具文档为准，本技能维护选用原则，不重复保存整套 CLI 命令。写入后核验结构和样式；图示需检查实际呈现。平台不支持目标形式时，采用能保留信息关系的可用形式，不声称已实现不存在的样式。

**为什么这样要求**

原生组件能够直接表达信息结构与强调关系，并便于读者后续编辑。只用文字模拟样式，会使文稿失去应有的阅读效果；按任务加载工具说明可以避免格式语法过时。

**正反例**

- 构造反例：在飞书正文中写“[绿色高亮] 0.8400”，用空格模拟表格对齐，或把“Callout”当作普通段落标题后声称已经完成高亮。
- 正例：创建原生评分表，在关键结果处实际设置浅绿色背景和加粗，将结果摘要放进原生 Callout，并核验写入后的内容与格式。

以上构造示例分别说明并列要点、评分表、背景色、表头、单元格列表与加粗的用法。指标、结果和资料均由实际任务提供，配色按本细则明确的约定执行。

## 10. 架构与流程画板

**适用条件**

当前任务已包含飞书文档创作、结构优化或相应章节的内容调整，且图示能明显降低理解架构、调用关系、数据流、分支汇合、状态变化、组织层级或方案差异的成本时，主动生成并插入原生画板，不必等用户逐一要求配图。已有适用图示时先按“素材复用”处理；现有画板需要更新时复用其 token，不另建重复画板。

只改一句、刷新数据、同步简短进度，或仅出现“架构”“流程”等词时不触发。只要求聊天中给文案时，不因此创建或写回飞书文档；精确数值查阅优先用表格，统计趋势按数据和图表能力选择载体，不把所有可视化都强制变成画板。

**规则与禁用内容**

- **生成与插入：** 先读取 `lark-doc` 的画板处理指南，由其负责文档位置与画板创建；复杂图的创作及已有画板编辑调用 `lark-whiteboard`，按当前 CLI 工作流执行，所需子智能体协作也遵循该流程。简单图可由文档 CLI 直接生成原生画板。不在本技能复制命令、格式或固定图形语法，不停留在“建议加图”、源码或空白占位画板。
- **信息选择：** 一张图解释一个主要关系，只保留示意图、节点名称和必要的分组、连线、分支短标签。宏观架构图优先呈现核心职责和运行边界，关键配置、鉴权及主要交付按本次关注点保留；输入构建、缓存、水位、重试等内部步骤仅在需要判断这些机制时展开，不因实现中存在就默认入图。画板内不放整句的描述性标题、解释段落或底部说明；必要解释放在相邻正文，正文已有时不重复添加。不能把整句说明拆成多行或塞进节点来规避。节点和连线以当前材料为依据，明确方向及必要分支；不能为凑出完整架构编造模块、调用或因果。关系缺少依据时保留不确定性。多个独立问题可分图，避免压成一张难读的大图。
- **布局与配色：** 主流程方向一致，同类节点尺寸、对齐和间距统一，合并不影响理解的中间状态，避免大面积空洞和不必要的绕行。优先通过布局实现直线连接；分支标签绑定连线，节点标签放在节点内，不用游离文本框补充说明。按数据、决策、执行和结果等实际职责区分协调的配色，同类保持一致；不将所有节点铺成同一种颜色，也不为增加颜色任意拆分职责。
- **插入位置：** 放在首次需要理解该关系的对应章节，通常位于简短概述之后、逐模块或分支细节之前；前后方案比较图靠近方案比较段。图示替代重复的关系描述，正文保留必要结论、限制和精确数据，不逐节点复述；不将所有图统一堆到文末，也不移动未获准修改的定稿内容。
- **完成核验：** 回读文档，核对画板位置和实际内容，并检查画板 CLI 导出的实际预览；不能以“已下载”“文字可读、线已连上”代替视觉检查。逐项检查标签是否位于对应节点或连线上、有无多余说明、连线是否绕行或相交，以及整体对齐、间距、留白、配色层次和图文一致性；按文档展示尺寸检查可读性。有问题就在当前画板修正并重新核验。仅创建 token、生成本地代码或插入空白画板不算完成。已有原生画板复制失败时，仍遵循“素材复用”的处理边界，不借此擅自重绘替代。

**为什么这样要求**

画板能让读者直接看到文字中分散的连接、层级和分支；插在对应论述旁可以减少往返查找。原生画板便于继续编辑，完成插入与预览核验才能确认读者实际看到的是可读的图示。

**正反例**

| 当前内容 | 正例 | 反例与问题 |
|---|---|---|
| 架构材料已明确请求入口、Planner、执行器、工具及返回路径 | 在架构概述后生成调用关系画板，标清方向，随后说明关键模块职责 | 只写“此处建议放架构图”，未生成和插入，读者仍需自行拼接关系 |
| 审核流程存在通过、驳回、修改后重提三个分支 | 在流程概述后插入分支画板，展示回到哪一步；操作入口仍放在对应步骤中 | 把各段原文逐句装进矩形，连线不标条件，无法看清分支 |
| 两个方案的调用路径不同，需要读者比较 | 并排画出两条路径，沿用相同模块名称，突出实际变化，放在方案比较段旁 | 两图名称和方向不一致，使排版变化被误认为架构变化 |
| 构造画板展示查询预处理与目录检索的调用关系 | 只画节点、连线及“并行”“enabled / disabled”等短标签，解释放在正文 | 在图顶写“当前链路：目录检索位于请求等待路径”，图底再写“预处理完成时，检索可能已经开始”，让画板重复承担正文说明 |
| 周报只有“架构方案已评审，待开发” | 保留简短进度说明 | 因出现“架构”就补画缺少依据的系统图，扩大范围并引入虚构信息 |
