# 内容组织细则

目标与受众决定文档需要解决什么问题，材料整合决定哪些信息共同服务于一个章节目的，信息顺序决定先讲什么，标题划分决定在哪里分节，方案依据说明为什么这样做，详略安排决定当前正文展开到什么程度。共同约束与标题要求遵循[主文件](../SKILL.md)，标题改写参考[表达范例](prohibited-expressions.md#5-标题命名)。

## 1. 目标与受众

**适用条件**

撰写或调整内容时，按读者本次需要完成的理解、判断或操作任务确定内容深度。

**规则**

写作前明确读者本次的任务与已有背景，据此选择内容范围、术语解释和技术细节：

- **管理决策：** 提供影响决策的问题、价值、结果和待决事项。
- **架构设计与方案评审：** 说明模块职责、输入输出的业务含义、数据流转、依赖与并行关系、决策条件及失败处理；正文、标题、表格和画板使用读者能理解的职责名称。具体接口或协议本身属于评审对象，或标识影响兼容性判断时，保留必要的准确标识；其余实现细节留在实现或操作资料中。
- **实现评审、联调、操作指导与 Skill 说明：** 提供执行和验证所需的准确接口、命令、参数、输入输出约定及判断条件。

读者缺少相关背景时，先补充理解当前内容所需的背景和链路；需要实际上手时，再给出必要操作前提与细节。需要向读者交代文档定位时，简要说明目标与受众。

**为什么这样要求**

同一事实对不同读者的作用不同。先明确读者及阅读目标，才能判断哪些背景必须解释、哪些技术细节有助于理解或执行，减少无关信息造成的阅读负担。

**正反例**

- 新人指南反例：架构开头列出 Agent 与 Tools 的 PSM、接口路径和部署端口，直到后文才说明用户请求如何被处理。
- 新人指南正例：先说明“理解需求 → 规划步骤 → 调用业务能力 → 组织回答 → 承接后续问题”，通过选品接续创作的例子解释信息流转；开发上手部分再给出启动与验证所需的入口。
- 管理汇报反例：用大段接口名称和配置参数介绍项目进展，却没有说明解决的业务问题和实际结果。
- 管理汇报正例：说明业务问题、方案变化、已验证收益和待决策事项，将具体接口配置放入技术资料。
- 技术文档反例：只写“调用工具完成处理”，没有说明工具的作用和调用关系。
- 技术文档正例：写明商品搜索工具接收哪些查询条件、返回哪些商品信息，以及这些结果如何进入后续生成环节；联调时提供对应接口和端口的用途。
- 架构设计反例：`将 board_availability.py 拆分，复用 warm_us_board_category_cache，再把 available_categories 写入 state。`
- 架构设计正例：`榜单可用性检查与类目匹配分别负责数据准备和语义判断。系统复用每日榜单缓存，与达人画像并行读取，再将可用类目交给匹配模块。`
- 章节命名反例：章节解释是否执行类目匹配的条件与优先级，却直接以 `query_category_gate` 作为标题，让读者先理解代码标识。
- 对应正例：标题使用“门控机制”；只有需要定位实现或评审接口时，才在正文保留相应标识。若文档比较多种门控，可用“类目匹配门控”区分，名称按实际阅读用途选择。

## 2. 材料整合

**适用条件**

本次任务需要从参考资料提取、核实或整合内容时适用。用户只要求润色已有文案或修改格式时，不自动扩大为外部资料调研；仅引用一个已明确用途的入口，也不要求递归读取其所有关联文档。

**规则与禁用内容**

使用多份参考资料时，先判断每部分信息帮助读者理解什么、回答什么问题，再按共同的章节目的整合。来源文档的类型、名称和原有目录用于查证，不直接决定新文档的章节分类；标题应准确概括整合后的内容及其作用。

整合某项事实、流程或图示前，阅读支撑它的来源内容；当前资料只是摘要或索引、缺少必要依据时，沿相关引用继续查阅。查到足以支撑当前主题的信息即可，不要求递归读完所有无关链接，也不能仅凭文档标题推断内容。

用案例论证常见不足或未来迭代方向时，先核实同类问题在多个独立对象中的重复出现，记录统计范围、请求数、去重会话数及时间分布，再选证据完整且类型互补的代表例。评分标签只用于召回，不能直接当作核实频次；单次偶发现象仅作为个例，不外推为普遍问题。先阅读已有案例和结论，避免重复其已覆盖的方向。

不要因为来源包含业务介绍、PRD 和技术方案，就机械设置“业务与产品”“PRD 介绍”“技术资料”等章节。抽象到能统摄本节内容、又能让读者辨认用途的层级即可，避免用“相关内容”等空泛名称，也不将实际目的不同的材料强行合并。

**为什么这样要求**

不同类型的材料可能共同解释同一个问题，一份材料也可能服务于多个章节。按来源分类会把查资料的过程带入文章，割裂读者需要连续理解的内容；按章节目的整合，能让背景、问题和目标形成完整说明。阅读实际来源，可以防止仅凭标题或摘要补出未经证实的内容。

**正反例**

- 反例：新人指南同时引用内容电商介绍、联盟资料和 Agent PRD，于是将章节命名为“业务与产品”，分别概述每份资料。
- 正例：这些资料共同解释业务背景及 Agent 的目标，整合为“业务背景和目标”：从内容电商的整体链路说明联盟的角色，再从达人经营中的问题引出 Agent 的任务和目标。
- 另一组反例：因为证据来自访谈和实验报告，就把同一个方案依据拆成“访谈内容”和“实验报告”。
- 对应正例：按待解释的问题组织方案依据，在同一处结合相关访谈发现和实验结果，保留各自来源。
- 来源阅读反例：看到“模块文档地图”的标题，就据此补写节点职责和调用顺序，没有阅读实际设计资料。
- 来源阅读正例：从文档地图进入相关设计资料，核实当前章节要讲的主流程，并检查其中可复用的架构图；无关模块不继续展开。

## 3. 信息顺序

**适用条件**

撰写或修改连续说明时，检查分句、句子和段落之间的关系；组织多项内容时，按实际的理解、决策或执行依赖排序。独立字段、短状态项和并列条目可直接并列。

**规则**

必要前提放在依赖它的内容之前。局部对象需要整体背景时，先交代整体，再说明该对象如何回应前文需求。

承担操作指导的部分按实际执行顺序编号，将已有的前置条件放在相应操作之前，就近提供所需入口、示例和已有的完成判断。前提与步骤依本次任务及材料确定，步骤内的并列选项可用 bullet point。进展同步和方案讨论按其阅读任务组织。

介绍工作或方案时，目标尚不清楚就先简要说明问题、目标或用途，再展开动作与结果。前文已交代背景，或本次只接续已有进展时，直接写增量。

句内、句间及段落之间写清实际的因果、转折、补充、递进、条件或先后关系。语序、指代和关键词承接已能表达关系时，直接沿用；需要时再添加相应连接词。

引导句点明当前问题或讨论对象，并统领后文；后接列表时，概括范围应覆盖实际条目。新段落或新章节开头不直接以“因此”等依赖前文的连接词起句，先点明本段要回应的问题或讨论对象；同一段内前提明确、因果紧邻时，仍可使用相应连接词。前文已说明对应关系时，简短引出或直接进入列表。

**为什么这样要求**

前提前置让读者在理解或执行时获得必要信息；写清内容之间的关系，能让读者理解后一项如何推进前文。引导句则说明后续内容共同回应什么问题。

**正反例**

以下示例来自类目匹配优化文档的评论。

- 反例：`按域门控已减少无需榜单的请求等待。它无法区分同一子意图下的不同模板。系统需要增加模板级配置。`
- 正例：`按域门控已减少无需榜单的请求等待，但无法区分同一子意图下的不同模板。因此，要让模板独立决定是否执行类目匹配，系统还需要增加模板级配置。`

## 4. 标题划分

**适用条件**

获准新建或调整章节结构时适用。仅修改句子、数据或格式时，不据此拆并标题；已有简短文稿也不必为了满足此规则新增章节。

**规则与禁用内容**

设置标题时，同时判断内容之间的主题差异和标题下的实际篇幅。只有当前内容与上一节的主题差异明显，且已有足够内容形成独立单元时，才新起标题。两部分内容接近、相互补充或前后延续时，应在同一节中通过分段展开。

独立段落中的短名称如果实际统领一组说明或整张结果表，并有目录定位价值，就使用对应层级的原生 heading，不用加粗正文模拟小标题；判断内容量时包含表格，不只看说明文字多少。例如“复测口径”“分项 GSB”“分意图 GSB”分别统领实验口径和不同范围的结果表时，可设为同级小节，并检查评分结果没有误落在“口径”或“GSB”标题下。单条 bullet 内的“重复实验：”等标签仍用加粗；周报项目标签和一句补充说明不因此升级为 heading。

禁止稍有一点内容就新起标题；禁止为一句补充说明、一个资料链接或同一主题的后续步骤单独设置小节。内容虽有区别但篇幅很少时，可在合适的现有章节中用短段落说明。只有笼统分类作用、没有独立概述或定位价值的上层标题可在获准调整结构时移除，让已有独立主题直接成节；同时调整必要的子标题层级，保持原有从属关系，不把后续并列内容误归入前一主题。不要为满足分节而凑字数，也不要设置固定字数或段数门槛。

**为什么这样要求**

每个标题都会引入一次阅读切换，并在目录中占据一个位置。相近内容被拆成过多的小节，会割裂说明、增加目录负担；标题下只有少量文字时，这种切分往往没有提供足够的定位价值。

**正反例**

以下例子对应同一段评测入门介绍，两种评测仅有简要说明：

反例：

```markdown
## 节点评测
节点回放在固定输入上对比节点输出。

## 端到端评测
端到端评测用于评估完整任务的完成情况。
```

正例：

```markdown
## 效果评测
节点回放在固定输入上对比节点输出。

需要评估完整任务的完成情况时，使用端到端评测。
```

这里将紧密相关的简短说明保留在同一节中。分节依据是实际主题差异和内容量，不能仅因为出现两个术语，就分别设置标题。

- 冗余层级反例：用没有概述内容的一级标题“节点设计”包住已有完整说明的“门控机制”等独立主题，读者需多经过一层笼统分类。
- 对应正例：用户要求取消这一层时，将“门控机制”提升为一级标题；原有并列章节和必要子标题相应调整，正文与既有顺序保持不变。承担真实分组或概述作用的上层标题继续保留。

## 5. 方案依据

**适用条件**

当前内容需要帮助读者理解、选择或评审一种方案，且问题与做法的对应关系尚不清楚时适用。仅汇报已知方案的进度或结果时，不强制重述背景、动机和完整论证。

**规则与禁用内容**

需要说明方案选择时，交代它针对的具体问题，让问题与做法对应起来。已有上下文已说明的依据无需重复。

**为什么这样要求**

读者需要理解为什么选择这些方法。明确对应的问题，有助于理解方案的作用，并判断自己的问题是否与之相关。

**正反例**

- 反例：方案包括跨域信号引入、样本优化和特征优化。
- 正例：针对泛低活用户行为数据稀疏、模型预估偏差大的问题，引入跨域信号，并优化样本与特征。

## 6. 详略安排

**适用条件**

选择内容详略时普遍适用；其中资料位置规则仅在确有延伸阅读资料或操作入口时触发，注释规则仅在需要判断某项补充是否必要时触发。不要求每个章节都有引用、每个判断都有注释或每篇文章都有操作说明。

**规则与禁用内容**

当前正文保留完成阅读任务所必需的信息。确有深入查阅需要且存在相关资料时，再提供引用；不为简短周报或需求描述强行创建延伸材料。禁止只给链接、让读者跳转后才能理解当前论述；也不要把引用资料的全部细节重复搬进正文。

供进一步阅读的参考资料放在对应小节末尾，可用引用块配合列表呈现；完成当前动作所需的入口、示例任务和操作教程紧邻对应步骤。当前操作只有一个入口时，直接内嵌到说明句中；同一步骤下有多个需要读者选择或分别查阅的并列入口时，使用紧邻说明的引用块，在块内以 bullet point 逐项列出，让读者能直接辨认并点击。属于不同步骤的入口分别就近放置，不因全文链接较多就集中成组。禁止把各节参考资料集中到独立附录，让读者反复跳到文末寻找来源；不为放链接单独新起标题。

资料名称和所在位置已能说明用途时，直接保留引用，不为每条资料机械追加“介绍……”“提供……”“解释……”等说明。只有读者需要据此区分入口或选择资料时，才补充简短用途。

技术细节按阅读用途取舍：讲解方案写职责、机制和数据流；评审接口或指导操作时保留准确的 MCP/API 名称、参数和必要代码；Skill 保留执行所需的命令、输入输出及判断条件。与当前理解、判断或执行无关的调用过程、执行日志和代码从正文删除，确需查阅的实现资料就近链接。用户指定展示的内容按其要求保留。

设计文稿默认不增加执行者的测试、验收、灰度或自检清单；用户明确要求，或这些机制本身是设计对象时，才展开相应流程。

只保留影响当前结论、数据解释或操作的注释、澄清和限定说明，并就近简短呈现；其余删去。资料溯源放在对应小节末尾有实际查阅用途的引用中。

**为什么这样要求**

读者应能在当前文稿中形成必要的理解，同时在需要深入时知道去哪里查阅。引用紧随对应小节，能减少往返文末查找和辨认资料用途的负担。这种安排兼顾连贯阅读和按需查找，也避免主线被旁支细节打断。

**正反例**

- 反例：VT：详见相关文档。
- 正例：VT 是排序融合分的计算模块。公式配置见使用手册，实验参数调整见变更说明，算分排查使用 VT 调试工具。
- 冗余注释反例：新人指南列出观测指标后，追加“以上指标沿用 1.0、2.0 LR 的名称。比较时保持统计周期、实验人群和达人分层一致……”。
- 对应正例：指标表后不追加这段说明，将 LR 链接放在本节末尾供读者查阅，再衔接下一部分。
- 引用位置反例：系统架构一节没有资料入口，读者需要跳到全文末尾的附录寻找架构设计文档。
- 引用位置正例：在系统架构一节末尾，用引用块列出模块文档和融合设计的原生引用；名称不足以区分用途时，再补充简短说明。
- 引用说明反例：“架构资料”下每条文档都再写“提供架构资料入口”“介绍相关设计”，重复标题已经表达的信息。
- 引用说明正例：“架构资料”下直接列出能辨认内容的原生文档引用；需要区分调试入口和发布入口时，再分别说明用途。
- 操作入口反例：要求读者申请 HDFS 权限，却把申请入口统一挪到节末，和其他背景资料混在一起。
- 操作入口正例：在“申请数据权限”这一步直接提供权限申请入口；补充的原理资料留在节末。
- 多入口反例：把 MCP 与 Agent 两个编译入口都塞进操作长句，或集中放在整套流程之后，增加逐项查找成本。
- 多入口正例：编译说明后紧接一个引用块，块内用两个 bullet point 分别列出 MCP 编译流水线、Agent 编译流水线，再接操作截图；FaaS 的两个入口同样放在 FaaS 步骤旁。单独一个权限申请入口仍内嵌在对应说明句中。
- 关键注释正例：某项实验结果实际只覆盖 L2 达人，且正文容易被理解为全体达人时，在该结果旁简短标注“统计范围：L2 达人”，防止将分层结果外推。

正例中的资料名称在实际文稿中应对应真实、可访问的引用，不得编造链接。

以上正反例使用构造的新手指南与技术说明场景，说明信息顺序、方案依据与详略安排。

## 7. 局部补充与衔接

**适用条件**

在已有文稿中补充介绍、强调差异、澄清概念或按评论修改时适用。“额外增加”“强调一下”首先表达内容需求，不直接指定新增段落、章节、注释或高亮块。用户明确指定呈现形式时遵循其要求；从零创作或获准重构时，可按阅读任务重新组织。

**规则与禁用内容**

修改前，阅读锚定内容、前后段落及同类条目，判断新增信息与现有内容是并列、前提、因果、条件还是先后关系，再决定位置和写法。并列对象补入现有列表或表格的同级位置；概念差异、前提和流程关系优先融入首次需要它们的引导句或步骤说明。位置依据实际关系或用户指定，不按请求中出现词语的顺序机械追加。

沿用所在部分的层级、编号、加粗标签、句式、语气和说明深度，使新增内容像原文的一部分。不能只复用字体颜色，却留下重复解释、突兀转折或孤立的补充段。

仅当内容承担独立的阅读任务、确有必要单独查阅，或用户明确要求时，才新增段落、章节或提示组件。强调差异时，要把差异对理解或操作的影响写入叙述，不能只另起一句“注意区分二者”。完成后连读前文、修改处和后文，检查信息是否放在需要它之前、同类条目形式是否一致，以及是否仍有重复或需要读者自行拼接的关系。

**为什么这样要求**

局部修订既要补足信息，也要维持整篇文稿的阅读连贯性。将每条反馈都作为独立补丁追加，会让读者自行关联新旧内容；融入原有叙述才能真正降低理解成本。

## 8. 作业

按题设组织解答，展开必要的建模、计算、方法比较和结果讨论，按要求保留文献引用和数据来源。作业正文不附“依据：……”等额外说明，也不以“参考课件”“解题依据”标签变相保留；不加采用口径的自述或题目未要求的预防性否定。影响解答的材料疑点在沟通中说明。
