# 完整检查与修订流程

每次触发 writing-style 都执行本流程，覆盖撰写、改写、润色、审阅和局部修订。它负责防止漏项，具体写法仍由各规则源维护，不另设一套文风或配色标准。

## 1. 明确范围并读取内容

- 从用户请求与上下文确定受众、阅读任务、交付形式、可修改范围和已有定稿。“润色”同时包含语言通顺和降低理解成本：在授权范围内按读者的理解顺序重排信息，保留理解重点所需的背景与因果，删去分散注意力的细节；不能只替换措辞或追求字数最少。面向缺少相关背景的读者时，先让读者看懂具体问题或变化，再引入必要术语，避免让读者自行补足前提。用户说“用这套 skill 改造／润色全文”时，默认包含文风、组织、论据与呈现的完整处理；不能自行收窄为排版，也不要求用户逐项点名。
- 全文任务读取全文及其结构；局部任务读取目标内容、相邻上下文和相关同类条目。新写作先读取已有素材，成稿后按同一流程审阅。飞书任务通过对应技能读取原生块、样式、资源与必要的评论上下文，不能只根据纯文本判断排版。
- 每次读取主文件、[禁用表达](prohibited-expressions.md)、[内容组织](content-organization.md)和[信息呈现](information-presentation.md)的适用条件与规则。下表逐项判断后，再加载相关的周报、表格案例、编号核验等参考；不预读无关平台命令或不适用场景的全部范例。
- 区分作者叙述、引用的原文、模型回答、代码、数据和用户实时修改。表达修订不能改写原始证据；新读到的用户改动优先保留。

## 2. 建立覆盖记录

按下表检查全部维度，再将适用规则源中的各条要求落实到具体段落、表格、资源或条目。下表是导航，不能勾选一个大类就视为该文件全部规则通过；也不能只做关键词检索而不理解上下文。

| 检查维度 | 需要判断的问题 | 规则入口 |
|---|---|---|
| 受众与任务 | 读者需要理解、决策、同步进展还是执行操作；详略是否匹配 | [内容组织 §1](content-organization.md#1-目标与受众)及主文件场景路由 |
| 事实与原始数据 | 数字、字段、状态、范围、条件和不确定性是否保真；是否混淆预期、能力与实测效果 | 主文件“公共规则与场景路由” |
| 论据与判断 | 分析是否由实际案例支撑；是否过度概括、错误归因或遗漏反向结果 | [内容组织 §2、§5](content-organization.md#2-材料整合)及适用的案例规则 |
| 用词与语气 | 词义是否准确；是否有夸张、模糊评价、口语缩略或不必要的中英夹杂；保留受众熟悉或用户指定的术语 | 主文件 §2 及[术语注释](prohibited-expressions.md#2-术语注释) |
| 句式、主语与指代 | 是否有机械对比、排比、无主语讲解或指代不明；句间逻辑是否清楚 | [禁用表达 §1、§3](prohibited-expressions.md#1-对比与排比) |
| 元话语与结尾 | 是否用写作预告、自我声明或空泛升华代替实际内容 | 主文件 §3 及[禁用表达 §4](prohibited-expressions.md#4-结尾评价) |
| 标题与层级 | 标题是否标识阅读重点；分节是否必要、层级是否连续；飞书章节编号是否为原生自动编号；案例名称是否混入无关对象细节 | 主文件 §1 及[内容组织 §4](content-organization.md#4-标题划分) |
| 主线与衔接 | 问题、做法、依据、结果是否按理解依赖展开；句内分句、句间与段间的实际关系是否表达清楚；引导句是否承接上文并准确统领下文；局部补充是否融入相邻叙述与同类格式 | [内容组织 §3、§7](content-organization.md#3-信息顺序) |
| 详略与信息归属 | 是否有重复与旁支；案例证据、公式定义是否仍与论据或所属对象相邻；是否错误地用跳转代替就近核对 | [内容组织 §6](content-organization.md#6-详略安排)及[表格归属](information-presentation.md#2-结构化表格) |
| 并列条目与编号 | 独立要点是否分项、标签是否一致且能区分具体职责或变化；各句是否归入对应职责的条目；操作顺序与并列关系是否区分；编号疑点是否有原生证据 | [信息呈现 §1](information-presentation.md#1-并列要点)，有疑点再读[编号核验](numbering-verification.md) |
| 表格、案例与双栏 | 信息关系适合哪种形式；比较方向、资料完整性、列宽、合并及对齐是否合理 | [信息呈现 §2、§3](information-presentation.md#2-结构化表格)，按场景读[表格范例](table-examples.md)；长案例读[完整案例对比表](case-comparison-layout.md) |
| 数值结果与公式 | 单位、精度、差值方向、GSB 口径是否一致；数学排版是否贴合正文；是否擅自舍入或补造数据 | [表格范例 §2—§4](table-examples.md#2-训练结果表)及[原生组件](information-presentation.md#9-原生组件) |
| 强调与 Callout | 哪些关键结果或差异需要主动强调、当前是否遗漏；已有强调是否准确；加粗、颜色与字号是否协调；Callout 的浅底和同色边框是否成对设置 | [信息呈现 §4、§6](information-presentation.md#4-视觉强调) |
| 引用与操作入口 | 引用是否必要、原生且目标正确；是否与对应叙述就近；多个入口是否清楚并列 | [信息呈现 §5、§8](information-presentation.md#5-引用块)及[详略安排](content-organization.md#6-详略安排) |
| 图示与资源 | 图是否能降低关系理解成本；现有资源是否适用；需画板时是否真正生成、插入并核验 | [信息呈现 §7、§10](information-presentation.md#7-素材复用) |
| 目标平台格式 | 飞书等平台的表头、列表、公式、引用、Callout、画板是否使用正确原生组件，保存后属性是否符合规则 | [信息呈现 §9](information-presentation.md#9-原生组件)及对应平台技能 |
| 体裁要求 | 周报是否精简地体现问题、动作、影响与状态；技术说明是否保留必要依据；操作指导是否可执行 | 主文件路由及相应体裁参考，周报读[周报条目](weekly-status.md) |
| 评论与动态修改 | 是否只处理授权范围内的评论；是否读取锚定内容、保护用户修改、回读后再解决并复查 | 主文件 §7 及对应平台技能 |

为适用的具体规则保留紧凑的工作记录：`规则／内容位置／发现／处理结果／核验依据`。状态使用“已检查，无需修改”“已修改并核验”“不适用，附原因”“待处理或待核验，附原因”。不需要每次生成文件或向用户展示整张表；短文可简记，长文或跨多轮任务需保留可继续工作的逐项记录。

视觉强调的核验依据需落到具体结果或差异：说明选中了什么、依据是什么，并回读实际加粗或背景属性。仅记录“保留了用户高亮”不能证明已检查其他应强调但尚未强调的内容；用户补做的高亮不能记成智能体已完成的修改。

“不适用”必须基于任务或内容关系。例如，没有训练评估数据就不创建 GSB 表；聊天中的周报不适用飞书组件。但不能因为文档现在没有表格或画板，就跳过对是否需要它们的判断。工具不可用、资料不足、尚未检查属于待核验，不能记成不适用或通过。范围外内容保持不变，只有实质影响本次任务时才向用户说明。

## 3. 完成适用范围内的修改

先处理影响理解和正确性的事实归因、主线与信息归属，再逐段逐句修改作者文案，最后协调形式与平台样式。实际顺序可按依赖调整，但不能处理一个维度后就结束。

- **逐句检查文风：** 包括词义、句式、语气、主语、指代、术语、冗余和衔接；不能只替换几个禁用词，也不能只把英文词改成中文就算完成。专有名词、用户指定用语与原始回答按各自身份保留。
- **按关系组织内容：** 保留完成当前理解与核对所需的证据，整合同一论点的重复说明。深度改造不以改动数量、压缩比例、增加章节或把完整案例移到文末为目标。
- **逐对象检查形式：** 覆盖范围内每张表、每组列表、每处引用、每个 Callout 及其他适用组件都要检查，不能只修第一张表就默认其余一致。
- **持续保护用户修改：** 写入前重新读取当前目标，仅修改尚未被用户改动或可明确区分的不重叠部分；撤回用户否定的布局时保留其他已认可修改，不回放旧整篇快照。

只审阅的请求交付具体问题或按授权标注评论，不擅自改正文；只调整指定样式的请求完成该样式及其必要核验，不借完整检查改写定稿。遇到局部阻塞先完成不依赖它的工作，再准确说明剩余项。

## 4. 从成稿重新核验

修改后重新通读实际成稿，按覆盖记录逐项收尾；不要只核对补丁或沿用修改前的判断。

- 连读标题、正文、案例分析和表内资料，检查前后衔接、称呼、比较方向和信息归属，确认各处修改组合后仍然协调。
- 对照最新基线检查事实、数字、代码、原始回答、资源引用及用户定稿。发现证据不支持结论时修改作者分析，不能改造证据来配合结论。
- 外部文档回读保存后的内容与原生样式；需要视觉核验时使用用户允许的对应工具。未做视觉核验时只报告已确认的结构或样式属性，不能宣称页面效果已验证。
- 再遍历一次全部维度，查找遗漏的同类问题和修改引入的新问题。清单遗漏项、适用规则未核验、用户反馈未处理时，不得笼统宣称“已全面完成”。

对于全文改造，核验文风、逻辑与呈现是否都已检查，并用具体变化说明阅读改善，例如消除错误归因、让证据就近、修正不明确的标题、减少冗余和横向滚动。并非每个维度都必须产生改动，原本合适的部分可保留。

## 5. 交付与停止条件

适用范围内的问题已处理、成稿已回读、全部维度均有检查结果后交付。存在真实阻塞时明确未完成项与原因，不能用“全面优化”掩盖部分完成。

默认交付用户要的正文或在线文档，简短说明有代表性的变化与实质限制；不要把内部检查表写进成稿，也不默认附一份冗长审计报告。已有规则足够时不要再因每次执行遗漏堆叠同义规则。

## 场景对照

| 请求 | 应有行为 | 应避免的行为 |
|---|---|---|
| “用 writing-style 改造这篇飞书评测文档” | 检查全文用语、句式、证据、组织及每张表的原生格式；案例资料与分析就近；改后按全部维度复核 | 只改表头颜色和案例标题，直接称已完成 |
| “润色这条周报” | 在这条内容内检查事实、文风、组织及周报特点；直接给精简成稿，平台格式按实际交付判断 | 强加论文式章节、表格或画板，把检查流程写进周报 |
| “只把这张表的表头改为中蓝色” | 保留指定内容，完成表头样式核验；其他维度记录范围判断 | 以完整 review 为由改写正文、重排案例 |
| “改好后别用 Chrome DevTools” | 使用允许的 CLI 回读内容与样式，准确说明视觉核验的限度 | 偷用浏览器，或把 CLI 成功等同于视觉效果通过 |
