# 完整检查与修订流程

全文审阅、复杂修改或跨轮续做时使用本流程，在授权范围内逐项检查并记录。简短、自足的写作或润色按主入口完成成稿核对。

## 1. 明确范围并读取内容

- 从用户请求与上下文确定受众、阅读任务、交付形式、修改范围和已有定稿。全文改造包含文风、组织、论据与呈现；润色同时改善语言和理解顺序，保留必要背景与因果。面向缺少背景的读者时，先说明具体问题或变化，再引入术语。
- 全文任务读取全文及其结构；局部任务读取目标内容、相邻上下文和相关同类条目。新写作先读素材。飞书任务通过对应技能读取原生块、样式、资源与必要的评论上下文。
- 按下表判断哪些规则与任务有关，再读取对应参考的小节。具体表达有疑问时查[表达范例](prohibited-expressions.md)；实际编辑飞书时读取[飞书呈现细则](lark-presentation.md)的相关组件。
- 区分作者叙述、引用的原文、模型回答、代码、数据和用户实时修改。表达修订不能改写原始证据；新读到的用户改动优先保留。

## 2. 建立覆盖记录

按下表检查任务范围内的全部维度，将适用规则落实到具体段落、表格、资源或条目，并结合上下文作出判断。

| 检查维度 | 需要判断的问题 | 规则入口 |
|---|---|---|
| 受众与任务 | 读者需要理解、决策、同步进展还是执行操作；详略是否匹配 | [内容组织 §1](content-organization.md#1-目标与受众)及主入口“按需读取” |
| 事实与原始数据 | 数字、字段、状态、范围、条件和不确定性是否保真；是否混淆预期、能力与实测效果 | 主入口“共用规则” |
| 论据与判断 | 分析是否由实际案例支撑；是否过度概括、错误归因或遗漏反向结果 | [内容组织 §2、§5](content-organization.md#2-材料整合)及适用的案例规则 |
| 用词与语气 | 词义是否准确；是否有夸张、模糊评价、口语缩略或不必要的中英夹杂；保留受众熟悉或用户指定的术语 | 主入口“共用规则”、[用语范例](prohibited-expressions.md#6-用语规范)及[术语注释](prohibited-expressions.md#2-术语注释) |
| 句式、主语与指代 | 是否有机械对比、排比、无主语讲解或指代不明；句间逻辑是否清楚 | [禁用表达 §1、§3](prohibited-expressions.md#1-对比与排比) |
| 元话语与结尾 | 已有与新增内容中是否有可直接删除的写作预告、作者自证或空泛升华；必要事实与条件是否已融入正文 | 主入口“解释性与防御性声明”及[结尾范例](prohibited-expressions.md#4-结尾评价) |
| 标题与层级 | 标题是否标识阅读重点；分节是否必要、层级是否连续；飞书章节编号是否为原生自动编号；案例名称是否混入无关对象细节 | [标题范例](prohibited-expressions.md#5-标题命名)、[内容组织 §4](content-organization.md#4-标题划分)及[飞书编号](lark-presentation.md#1-标题与列表编号) |
| 主线与衔接 | 问题、做法、依据、结果是否按理解依赖展开；句内分句、句间与段间的实际关系是否表达清楚；引导句是否承接上文并准确统领下文；局部补充是否融入相邻叙述与同类格式 | [内容组织 §3、§7](content-organization.md#3-信息顺序) |
| 详略与信息归属 | 同一论点或规则是否分散重复；技术细节是否服务当前阅读任务；案例证据、公式定义是否与所属对象相邻 | [内容组织 §6](content-organization.md#6-详略安排)及[表格归属](information-presentation.md#2-结构化表格) |
| 并列条目与编号 | 独立要点是否分项、标签是否一致且能区分具体职责或变化；各句是否归入对应职责的条目；操作顺序与并列关系是否区分；编号疑点是否有原生证据 | [信息呈现 §1](information-presentation.md#1-并列要点)，有疑点再读[编号核验](numbering-verification.md) |
| 表格、案例与双栏 | 信息关系适合哪种形式；比较方向、资料完整性、列宽、合并及对齐是否合理 | [信息呈现 §2、§3](information-presentation.md#2-结构化表格)，按场景读[表格范例](table-examples.md)；长案例读[完整案例对比表](case-comparison-layout.md) |
| 数值结果与公式 | 单位、精度、差值方向、GSB 口径是否一致；数学排版是否贴合正文；是否擅自舍入或补造数据 | [表格范例 §2—§4](table-examples.md#2-训练结果表)及[原生组件](information-presentation.md#9-原生组件) |
| 强调与 Callout | 哪些关键结果或差异需要主动强调、当前是否遗漏；已有强调是否准确；加粗、颜色与字号是否协调；Callout 的浅底和同色边框是否成对设置 | [信息呈现 §4、§6](information-presentation.md#4-视觉强调)；飞书样式读[强调](lark-presentation.md#3-双栏与视觉强调)与[Callout](lark-presentation.md#5-callout-样式) |
| 引用与操作入口 | 引用是否必要、原生且目标正确；是否与对应叙述就近；多个入口是否清楚并列 | [信息呈现 §5、§8](information-presentation.md#5-引用块)、[详略安排](content-organization.md#6-详略安排)及[飞书引用](lark-presentation.md#4-原生引用) |
| 图示与资源 | 图是否能降低关系理解成本；现有资源是否适用；需画板时是否真正生成、插入并核验 | [信息呈现 §7](information-presentation.md#7-素材复用)；飞书画板读[创建与核验](lark-presentation.md#8-画板创建与核验) |
| 目标平台格式 | 飞书等平台的表头、列表、公式、引用、Callout、画板是否使用正确原生组件，保存后属性是否符合规则 | [飞书呈现](lark-presentation.md)及对应平台技能 |
| 体裁要求 | 周报是否精简地体现问题、动作、影响与状态；技术说明是否保留必要依据；操作指导是否可执行 | 主文件路由及相应体裁参考，周报读[周报条目](weekly-status.md) |
| 评论与动态修改 | 是否只处理授权范围内的评论；是否读取锚定内容、保护用户修改、回读后再解决并复查 | [评论修订](comment-revision.md)及对应平台技能 |

按 `规则／内容位置／发现／处理结果／核验依据` 保留可续做的逐项记录。状态区分“已检查，无需修改”“已修改并核验”“不适用，附原因”“待处理或待核验，附原因”。记录用于执行与续做，默认不另生成文件或展示整张表。

视觉强调检查具体结果和差异是否突出，回读实际加粗或背景属性；记录中区分用户已有或补做的高亮与本轮新增修改。

按任务与内容关系判断适用性，例如聊天中的周报不适用飞书组件。表格或画板的选用依据是信息关系；工具不可用、资料不足或尚未检查的适用项记为待核验。范围外内容保持不变，实质影响本次任务时再说明。

## 3. 完成适用范围内的修改

先处理事实归因、主线与信息归属，再修改作者文案，最后协调形式与平台样式；顺序按实际依赖调整。

- **逐句修订文风：** 按检查结果处理词义、句式、语气、主语、指代、术语、冗余和衔接；专有名词、用户指定用语与原始回答按各自身份保留。
- **按关系组织内容：** 将同一论点或规则归到最合适的位置，合并重复说明，按前提、做法与结果重组散落内容；保留必要证据，让案例与分析就近。
- **逐对象调整形式：** 处理范围内每张表、每组列表、每处引用、每个 Callout 及其他适用组件的问题。
- **持续保护用户修改：** 写入前重新读取当前目标，仅修改尚未被用户改动或可明确区分的不重叠部分；撤回用户否定的布局时保留其他已认可修改，不回放旧整篇快照。

只审阅的请求交付具体问题或按授权标注评论，不擅自改正文；只调整指定样式的请求完成该样式及其必要核验，不借完整检查改写定稿。遇到局部阻塞先完成不依赖它的工作，再准确说明剩余项。

## 4. 从成稿重新核验

修改后通读实际成稿，核对事实、用户要求与各处修改的衔接，按覆盖记录收尾。

- 连读标题、正文、案例分析和表内资料，检查前后衔接、称呼、比较方向和信息归属，确认各处修改组合后仍然协调。
- 对照最新基线检查事实、数字、代码、原始回答、资源引用及用户定稿。发现证据不支持结论时修改作者分析，不能改造证据来配合结论。
- 外部文档回读保存后的内容与原生样式；需要视觉核验时使用用户允许的对应工具。未做视觉核验时只报告已确认的结构或样式属性，不能宣称页面效果已验证。
- 完成记录中尚待处理的同类问题，检查修改引入的新问题及用户追加反馈。

全文改造用具体变化说明阅读改善，例如纠正归因、让证据就近、明确标题或减少横向滚动；原本合适的部分保留。

## 5. 交付与停止条件

适用范围内的问题已处理、成稿已回读、全部维度均有检查结果后交付；真实阻塞项说明原因与完成状态。

默认交付用户要的正文或在线文档，简短说明代表性变化和影响交付的未完成项，内部检查记录用于执行与续做。

## 场景对照

| 请求 | 应有行为 | 应避免的行为 |
|---|---|---|
| “用 writing-style 改造这篇飞书评测文档” | 检查全文用语、句式、证据、组织及每张表的原生格式；案例资料与分析就近；改后按全部维度复核 | 只改表头颜色和案例标题，直接称已完成 |
| “润色这条周报” | 在这条内容内检查事实、文风、组织及周报特点；直接给精简成稿，平台格式按实际交付判断 | 强加论文式章节、表格或画板，把检查流程写进周报 |
| “只把这张表的表头改为中蓝色” | 保留指定内容，完成表头样式核验；其他维度记录范围判断 | 以完整 review 为由改写正文、重排案例 |
| “改好后别用 Chrome DevTools” | 使用允许的 CLI 回读内容与样式，准确说明视觉核验的限度 | 偷用浏览器，或把 CLI 成功等同于视觉效果通过 |
