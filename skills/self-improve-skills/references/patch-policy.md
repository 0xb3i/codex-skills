# 自改进补丁策略

## 默认直接修改

凡是直接影响目标 Skill 成功率、正确性或效率，且本轮证据足够支持的必要改进，默认直接写最小补丁并验证；不要把明确问题留给用户决定。

## 可以自动修改

- 修正明显过时、错误或互相矛盾的 Skill 文案。
- 将本轮已验证的边缘情况、失败恢复或更简单路径提炼为适用条件与处理方法；修复共同原因，不为每个样例追加永久分支。
- 改善触发描述，让 Skill 更容易在正确场景被使用。
- 给已有脚本补一个小的错误处理、参数说明或最小自检。
- 删除明显重复、误导或与实际工具不符的说明。

## 技能来源与结构治理

- 修改前识别来源：`~/.codex/skills` 中的用户维护技能、安装器管理的 `~/.agents/skills`、以及官方/第三方插件缓存。路径本身不证明归属，结合软链接、安装清单和更新方式确认。
- 优先在用户可维护的源目录修正；安装器和插件缓存中的上游技能不直接打补丁，以免更新覆盖。专有业务场景放入职责明确的用户技能，按需引用上游能力；修复上游错误时更新其真实开发源并按安装流程部署。
- 用户明确要求拆分、去重、合并或重构技能时，授权范围内的结构调整直接实施并验证；下节限制适用于普通执行后自改进，不能阻断明确授权的维护任务。
- 结构治理检查每条规则的唯一归属、description 的实际触发、引用目标是否存在且可加载，以及是否形成相互强制触发。相邻技能只在真正需要其能力的分支引用，不以新总管或每任务审计增加常驻流程。

## 只记录候选，不自动修改

- 只是潜在影响、证据不足的优化、隐蔽风险或不确定泛化；不能仅因收益在长期体现就搁置已有充分依据的必要改进。
- 改变安全边界、审批策略、权限模型或生产操作流程。
- 写入密钥、token、账号、完整内部配置或无法脱敏日志。
- 大幅重组 Skill、引入新依赖、增加后台服务、hook、daemon 或数据库。
- 修改多个无关 Skill，或把一次偶发失败提升成通用规则。
- 用户的真实意图不清楚，且误改会影响后续任务。

记录候选后，在最终回复里告诉用户：候选是什么、为什么没有当下自动改、是否建议现在迭代。

## 验证最低要求

- 修改任何 Skill 后，运行 skill-creator 的 `scripts/quick_validate.py <skill-folder>`；先按技能目录定位，当前用户安装通常位于 `${CODEX_HOME:-$HOME/.codex}/skills/.system/skill-creator/scripts/quick_validate.py`，不要假设命令在 PATH 中。
- 修改脚本后，运行该脚本的最小 smoke test；没有测试入口时加一个轻量 `--help` 或 `__main__` 自检。
- 模型行为评测与回归遵循主技能的手动触发边界；用户明确要求后按 [评测流程](evaluation.md) 使用独立子智能体，不泄露预期答案或诊断。格式校验及确定性脚本测试不能宣称模型行为已通过。

## 写法偏好

- 一句能解决就一句；以能覆盖同类问题的最小充分规则为准，不用空泛口号，也不以文字最少为由只修当前单例。
- 根因修在共享入口，不在每个调用处补丁。
- 记录“为什么现在要改”，不要记录完整对话流水。
- 保留目标技能已有且有依据的限制，不引入无来源的样例阈值或与当前技能无关的约束。
