# 从现象到方法规则

以下均为构造示例，只展示查因与提炼方法，不是元技能需要执行的领域规程，也不代替独立评测。

## 产物失败：补足完成条件

用户说：“这次打出来的压缩包又打不开，上一回也是。”

查因发现：归档流程仅凭压缩命令退出成功就交付，未检查产物；生成文件的读取校验确实失败。

- 判断：完成条件缺少产物验证，属于归档技能的方法缺陷。用户没有提出一个新的个人偏好。
- 适当规则：“归档生成后，用对应格式的读取工具枚举条目并核验所需内容可读取；校验通过后再交付，不能仅凭生成命令退出成功判定完成。”
- 边界：不固定包名或重试次数，不推广为所有任务都需要归档校验。若原流程已明确要求这项校验而本次漏执行，应修正当前产物并检查遗漏原因，不追加同义规则。

## 状态误报：区分接受与完成

用户说：“任务还在排队，你却说已经处理完了。”

查因发现：工具契约确认这是异步提交，成功只返回任务标识，另有状态查询；当前技能把提交成功当成处理完成。

- 判断：应修正所属技能的完成判定，不能只为本次任务加特判。
- 适当规则：“异步提交成功仅表示任务已被接受；依据已确认的状态查询能力判定处理结果。尚未到达终态时，如实回报处理中，不宣称完成。”
- 边界：不推断所有接口都异步，不编造轮询间隔、超时值或尚未核实的参数名。若缺少契约或执行证据，先核实，不把猜测写成规程。
