# 提炼与归属示例

这些例子用于判断规则质量，不是需要复制到 AGENTS.md 的规则清单。

## 偶然细节与稳定方法

观察：一次页面操作依赖动态生成的容器 ID，页面更新后失效。

- 绑定单例：“以后找到容器 `panel-8472` 再点击。”
- 空泛提醒：“以后注意兼容性。”
- 可复用的方法：“定位交互目标时优先依据稳定语义属性，并验证目标唯一性；具体 ID 只有在它属于稳定接口契约时才可依赖。”

第三种写法保留了判断条件，通常归浏览器或开发 Skill。一次页面故障不足以推定用户在所有项目中的偏好。

## 偏好的适用范围

用户在 DECC 任务中明确说：“以后每个任务只交付一个最适合使用的最终文件。”

这是跨任务交付偏好，可以写入全局 AGENTS.md，保留用户要求多份时的例外。某个文档工具如何合并或导出文件属于对应 Skill，不能因为服务于同一偏好就把步骤复制进全局指令。

用户要求作业正文直接作答、保留题目要求的引用：这是作业写作的长期要求，归写作 Skill。先判断适用哪些任务，再判断是否值得持续保留。

若用户只说“这次发一份就好”，在当前任务执行，不推定长期偏好。

## 稳定约束与当前状态

项目规定：正式报告的指标定义以指定登记表为准；本周某指标处于临时试算状态。

项目 AGENTS.md 可以保存登记表的位置及出正式报告前核验口径的要求。本周的临时状态留在业务记录中，后续从登记表读取，不永久固化成指标规则。

具体信息本身并非缺陷：用户约定的分支、命名空间或权威配置路径可能是不可推导的必要定位信息；应按其适用范围保留，不能一律替换成“使用正确配置”。

## 已有规则与新发现

观察：现有规则已要求读取评论及锚定内容，但本次执行漏了读取步骤。

先检查是否加载了相关规则及为何漏执行，不再追加“务必读评论”“禁止不读评论”等同义句。只有发现规则缺少适用条件、描述未覆盖实际触发，或步骤确实不可执行时，才修订相应来源。

## 从具体表述提炼稳定要求

以下均为构造示例，只展示判断与适用边界，不是需要复制的个人约定或领域规程。

### 方案太多：提炼决策偏好

用户说：“五个方案都列出来了，我还是不知道选哪个。以后给我的方案建议，先告诉我最推荐哪个、为什么，再谈其他选择。”上下文确认指后续各类方案建议，而非仅本次采购。

- 稳定需求：建议应直接支持选择；“五个”和本次采购对象是偶然细节。
- 适当规则：“提供方案建议时，先给出推荐方案及关键取舍，再展开对当前选择有实质影响的备选。”归入用户长期偏好。
- 边界：不写成“采购最多列两个方案”，也不要求所有回答只能给一个答案；若用户仅说本次太长，就只调整当前答复。

### 评审混淆：保留项目契约

用户说：“后续评审还是这样：业务判断策略是否合理，法务确认合规。别看到一边‘已通过’，就把整个评审都当成过了。”负责人确认这是本项目长期采用的两项独立评审。

- 稳定需求：两个结论独立，不能相互替代；本次工单及日期不是规则的一部分。
- 适当规则：“本项目的业务评审与合规评审分别确认；只有两项均通过，才能将整体评审标记为完成。”归入项目约定。
- 边界：不要求其他项目一律双重审批。若该契约已被清楚记录，执行已有约定，不重复写入。
